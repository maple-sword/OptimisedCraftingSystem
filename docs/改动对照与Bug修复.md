## 1. 总览

一句话：**新模组把旧模组的「事后补救」改成「事前规划」**——旧模组在产物生成**之后**再想办法把它塞进容器，新模组在配方开始合成**之前**就先把「用哪件材料、产物存到哪里」算清楚，合成后只做一次落点执行与复核。

**(B) 新模组的「智能选材」在配方材料不可用时是整体放弃的，而旧模组是逐槽尽力。**
`PatchRecipeGetItemsForRecipe` 只要有一个槽位选不出材料就 `__result = null`（`PatchCrafting.cs:37-41`），行为与原版一致（原版 `Recipe.cs:139` 也是 `return null;`）；而 `GetItemsForRecipeThorough` 允许出现 `null` 槽位（`PatchCrafting.cs:73-74`，对应原版 `Recipe.cs:170` 的 `list.Add(null);`），所以「缺料时仍然显示图标」和「缺料时禁止合成」这两个语义分别和原版对齐，没有偷改原版行为。

## 4. 兼容性

### 4.1 与旧模组：**必须二选一**

新模组和旧模组补的是同一批方法（`Recipe.GetItemsForRecipe`、`Recipe.GetItemsForRecipeThorough`、`Settings.DefaultSettings`、`Locale.LoadLanguage`，见 §1 统计表），而且**沿用同一批设置名**（`ModSettings.cs:88-158`）。这意味着两件事：

1. **同时装上不会「两个都生效」**，只会互相抢补丁——旧模组那 5 个补丁都没有 `[HarmonyPriority]`、又是 `Prefix` 返回 `false` 的整体替换（`Patches.cs:10-13`），谁先谁后由 Harmony 内部顺序决定，结果不可预测；最坏情况是旧模组把新模组的会话补丁整个盖掉，玩家界面还在、行为却回到旧的。
2. **设置项会互相污染**：两边的设置名相同，游戏 `settings.json` 里只有一份值，旧模组改了开关，新模组读到的也是那个值。

因此新模组启动时会主动检测并报错提醒：`Plugin.WarnIfLegacyPluginLoaded()`（`Plugin.cs:68-82`）用 `Chainloader.PluginInfos.ContainsKey(LegacyGuid)` 查 `"com.balaur.BetterLogic"`（`Plugin.cs:28`、`:72`），命中就 `Log.LogError(...)`（`:74-75`）把「请先卸载旧模组」写进 BepInEx 日志，整段再包一层 try/catch（`:70-81`）以免检测本身出问题。

> 迁移方式：从 `BepInEx\plugins` 里删掉旧模组的 DLL（旧模组的程序集名是 `CraftingLogic`，`BetterInventoryLogic.csproj:7`，文件名容易和新模组混淆，删之前确认一下）。因为设置名相同，`settings.json` 里已有的偏好会被新模组直接继承。

### 4.2 与其它模组：刻意不引用三个程序集

新工程的头部注释把这条写成硬约束（`OptimisedCraftingSystem.csproj:3-16`），实现上：

- **不引用 Newtonsoft.Json**：语言表注入直接走 `Locale.currentLang.other`（`ModSettings.cs:389-392`），不自己序列化任何东西。
- **不引用 TextMeshPro**：所有自绘内容走 IMGUI（`UI\MaterialWindow.cs`、`UI\CraftOverlay.cs`），不碰原版的 TMP 层级。顺带一个具体理由：原版合成界面的材料预览图标是**按 TMP sprite 字符的出现顺序**摆放的（`PlayerCamera.cs:699-714`，判 `spriteIndex` 为 23/24），所以新模组追加的文本里**一个 `<sprite>` 标签都不能有**——这条纪律写在 `CraftText.cs:7-12` 的类头注释里。
- **不引用 UnityEngine.UI**：自建窗口用 `GUI.Window`（`MaterialWindow.cs:128`），只依赖 `UnityEngine.IMGUIModule`（`OptimisedCraftingSystem.csproj:61-64`）与 `UnityEngine.TextRenderingModule`（`:66-69`）。
- 工程**零 `PackageReference`**，也没有旧模组那样的 `BepInEx.AssemblyPublicizer.MSBuild`（对比 `BetterInventoryLogic.csproj:11`），8 个游戏程序集引用全部 `<Private>false</Private>`，不会把游戏 DLL 复制进输出目录。

这样做的直接收益：不会和 QoL Unknown 这类同样依赖 TMP / UnityEngine.UI / Newtonsoft 的大模组争抢程序集版本，插件目录里也不会多出重复 DLL。

### 4.3 与 CUCoreLib 等运行时扩展

新模组所有对外部注册表的读取都是「容忍未知」的写法：`Liquids.Registry.TryGetValue`（`CraftSelector.cs:313`、`QualityModel.cs:135`/`:178`/`:255`），未识别物品名回退到原版的 `Locale.GetOther("unknownobject")`（`CraftingScanner.cs:223` 的 `NameOf`）；液体名同理——`CraftText.LiquidName`（`CraftText.cs:99`）在注册表里查不到时直接显示 id 本身（真机上遇到过第三方塞进来的 `Blood O+`）。物品种类、工具、液体、性质、配方都由 `Recipes.recipes` / `Item.GlobalItems` 这类原版集合驱动，所以运行时注册的新内容会自动参与计算，不需要为新模组改代码。

### 4.4 与 QoL Unknown（ModOptionsMenu）：**唯一一处需要抢位置的高级冲突**

这条是本项目**唯一**一处"对方改写了原版方法、我们必须在它之前/之后抢位置"的情况（另有一次不涉及抢位置的崩溃处理，见 §4.5），取证方式是反编译装在同一台机器上的 `QoL Unknown.dll`（4325888 B）而不是猜：

- 对方的挂法（`QoL_Unknown.ModOptionsMenu.PatchExplicit()`）：
  `harmony.Patch(AccessTools.Method(typeof(SettingsMenu), "ResetToDefault"), new HarmonyMethod(typeof(ModOptionsMenu), "SettingsMenuResetToDefaultPrefix"))`；
  前缀体：`RebuildLiveSettingsAfterReset(); if (__instance != null) __instance.SelectTab(0); return false;`
  （`RebuildLiveSettingsAfterReset()` = `Settings.settings = Settings.DefaultSettings(); QoLModSettings.ResetCustomSettingsToDefault(); SyncRegisteredDefinitionsIntoLoadedSettings(false,false); Settings.ApplyAll(); Settings.SaveSettings();`）
- 为什么这会伤到本模组：Harmony 的前缀只要有一个返回 `false`，**原方法与其余前缀全部跳过**（后缀照跑）。对方 `Priority.Normal`(400) 先跑，本模组原来的 `Priority.Low`(200) 标记前缀被跳过 ⇒ `Attach` 没看到 `Resetting`，拿 `_lastKnown` 旧值做种 ⇒ 「恢复默认」对本模组 32 项静默失效。
- 本模组的对策（两条并存，见 §2 第 18 条）：标记前缀提到 `Priority.HigherThanNormal`(500) 先跑；再加 `Priority.Low` 后缀兜底，发现标记没置上就自己 `ForceReset` 一遍。
- 副作用评估：QoL 自己的 `RebuildLiveSettingsAfterReset` 仍然照常执行（它重建 `Settings.settings` 时会再次触发本模组的 `Attach`，这一次 `Resetting=true` 是真的），所以**对方的设置同步与界面刷新都没被破坏**；本模组只是在它之后把「记忆值」也清掉，多出来的代价是一次 `ApplyAll`+`SaveSettings`（点击级操作，无性能意义）。

其它第三方模组与本模组的入口先后关系（prosthetics 的钛合金手、CUCoreLib 的拾取前缀、CraftingTweaks 的缺料自动合成等）逐条列在 `docs\改进前后对比.md` §四点五。

### 4.5 与 Crafting Tweaks：一次真机实测到的崩溃与兼容垫片

和 §4.4 不同，这一条**不是抢位置，也不是我们和对方有矛盾**——是对方的界面增强恰好被我们的刷新调用拉进链子，然后炸在了原版方法的一个 null 假设上：

- 事实链（19:42 那轮日志 556-563 行，全日志唯一一条 Exception）：`UI\MaterialWindow.cs` 的覆盖层换材料 → `RefreshPanel()` 调一次 `PlayerCamera.RefreshCurrentlySelectedRecipe` → `CraftingTweaks.RefreshSelectedRecipePatch`（**后缀**，HarmonyId `kef.casualtiesunknown.craftingtweaks`）→ `CraftingTweaksUi.EnhanceIngredientPreviews` → `CraftingInventory.IngredientCountAvailable` → `ingredient.DoesUseItemType(item)` → **原版方法内部 NRE**。
- 责任在谁：原版 `RecipeItem.DoesUseItemType`（`RecipeItem.cs:78-116`）不给 `item` 做 null 检查（`:82`/`:106` 直接解引用，`:111` 用 `item.Stats.qualities` 而 `Item.Stats` 对未注册 id 会返回 null，液体分支 `:93-96` 在 `Liquids.Registry` 查不到时还会用 `value.qualities`）。这条方法本来只在"玩家自己点了某个槽位"的低频路径上被调用，是第三方（以及我们）把它的调用频率和调用语境改变之后才暴露的。
- 我们受的连带伤害：Harmony 会在某个后缀抛异常时跳过排在它后面的所有后缀，于是本模组用来复位面板标记的那个后缀被跳过（详见 §2 第 19 条的"连锁反应"栏）。
- 处理方式（19:48:58 版）：`Patches\PatchCompat.cs` 给这个方法挂 `[HarmonyFinalizer]`，只吞这一条异常并写一行带诊断的 `[Compat]` 日志；同时本模组的面板标记改成带帧号，跨帧残留自动作废。**对方逻辑一行没改**，对方下一次更新自己修好之后这条垫片就是死代码。
- 为什么选择"兜住"而不是"绕开"：绕开意味着不再在换材料后立刻刷新 C 键面板（玩家会看到消耗信息延迟半秒），而兜住只需要一条 finalizer——代价是万一原版判定真的错了，界面计数会偏低，界面上少算一件材料总好过每次换材料刷一条异常。

## 5. 仍未解决 / 已知取舍

这一节如实列出现状，不吹成完美。

1. **液体存放逻辑的彻底重做：只有方案，没有落地。**
   方案文档在 `OptimisedCraftingSystem\docs\流体存放逻辑重做方案.md`（263 行）。当前实际交付的是其中的 D 方案——**临时瓶与原版一致、5 分钟后连液体一起销毁**（§2 第 22 条，`PlacementPlanner.cs:267-297`）＋倒液改道（`PatchStorage.cs:79-111`）＋**手选落点时列出全部瓶子并标明内容物与不能用的原因**（§2 第 23 条，`PlacementPlanner.cs:349-419`）。**完整的液体台账 / 规则表**——也就是让玩家自定义「什么液体优先倒进哪类瓶子」——还没实现。
   文档里也核验了一条硬限制：原版 `Setting` 只有 `SettingBool`/`SettingInt`/`SettingFloat`/`SettingDropdown`/`SettingKeybind` 五种，而 `Settings.LoadSettings()` 的还原分支把这五种写死了（`Settings.cs:621-640`），**自定义设置子类的值永远还原不回来**，所以规则表只能落文件，做不成设置项。

2. **自定义消耗偏好（合成时优先消耗哪一件）：同样只有方案，没有落地。**
   方案文档在 `OptimisedCraftingSystem\docs\自定义消耗偏好方案.md`（238 行）。玩家现在能用的交互只有「在材料总览窗口或覆盖层的候选表里手动换掉某一槽的材料」（`CraftSession.RememberPick` `:103` ／ `ResolvePick` `:136` ／ `ApplyOverrides` `:156`，覆盖合法性由 `CraftSelector.Usable` 把关 `:54`）。**不能**自定义「优先消耗耐久最低的 / 优先消耗不在身上的」这类通用顺序——目前是模组预设的评分策略（`CraftSelector.cs:216-244`）。

3. **临时瓶在改道后可能空着。**
   原版的顺序是「先生成临时瓶、再往里倒液体」（`RecipeResult.cs:59` → `:63`），倒液这一步现在被新模组改道了（`PatchStorage.cs:98-100`）。如果这次倒液被成功改道到别的瓶子，那个已经生成的临时瓶就是**空的**；按 `PlacementPlanner.cs:290` 的规则，**我们自己做的**空瓶会在 30 秒后被清掉。要说准一点：**原版生成的那个**临时瓶挂的是原版自己的 300 秒（`RecipeResult.cs:64`，改道不会撤掉原版已经挂上的定时器），30 秒只作用于 `CreateTempBottle` 里「一滴都没装进去」的情形。相比原版的「空瓶也留 300 秒」，玩家的观感是「地上那个空瓶消失得更快了」——功能上没有损失，但确实与原版不同。

4. **「距离 ≥ 10 不装载」这条原版规则被保留，没有被绕过。**
   `Container.cs:124` 要求 `Vector2.Distance(item.transform.position, base.transform.position) < 10f`。新模组的规划器会提前按这条规则筛选候选容器（`PlacementPlanner.cs:391-421` 的 `Fits` 复刻了 `CanHoldItem` 的三个条件，`:424-446` 的 `ContainerCandidates` 只取 `body.GetSurfaceInventoryItems()`），所以玩家不会看到「计划好了却装不进去」的执行失败——但代价是**远一点的容器根本不会进入候选**，这是有意的保守选择。

5. **新模组不碰原版合成界面的层级。**
   材料总览是独立窗口（`UI\MaterialWindow.cs`），合成界面里只有一个覆盖层（`UI\CraftOverlay.cs`，20:02:54 版起贴在屏幕**右侧**、宽度 660、高度动态，20:51:19 版起可拖动、双击标题条复位，见 §2 第 20/21 条）。原版合成面板的控件是场景预制体，而 `RefreshCurrentlySelectedRecipe` 每次刷新都会销毁重建预览图标（`PlayerCamera.cs:682-693`），往里动态挂控件会被反复重建——所以「在原生合成界面里直接点选材料」这种更进一步的交互没有做。**素材选择改成了覆盖层自己的点击候选表**（`MaterialWindow.DrawPickList` / `DrawDestList`，`MaterialWindow.cs:793-921`）：点开的是我们自己的 IMGUI 列表，原版预制体一个节点都没动，所以原版刷新逻辑、第三方模组的后缀（含 Crafting Tweaks 的库存计数）都不受影响。液体落点的候选表同理——它列出全部瓶子（§2 第 23 条），被 `BlockedReason` 判为不可用的行置灰、`◀`/`▶` 也跳过（`MaterialWindow.cs:561-590`、`:882-887`）。

6. **未实现的旧模组 TODO。**
   旧模组 `Main.cs:7-21` 留了一串 TODO（显示容器总重、更好的拾取规则、自动整理、扩展物品信息、堆叠手动排序等）。其中「显示容器总重」由右键提示的 Shift 展开内容物覆盖（`PatchUI.cs:81-109` + `Hotkeys.ExpandHeld()`，`Hotkeys.cs:57-67`，复用游戏自己的 `expanddesc` 键位）；**自动整理、物品存在时长、堆叠手动排序这三项没有实现**。

7. **一个观感上的残留问题。**
   设置界面里模组新增项较多（沿用旧名的 19 项 + 新增 13 项 + 1 个按键项），而模组本身的说明文案只写在中英对照表与 `ModSettings.Bools` 的描述字段里。如果玩家用的是**第三方汉化包**且该汉化包比新模组旧，模组新增的 `ocs.` 项在设置界面里会显示为模组内置的中文（由 `Loc.IsChinese` 判定，`Loc.cs:96-117`），**与汉化包的措辞风格可能有细微差异**。这是「只补不覆盖」策略的必然代价（见 §3 语言键注入一行），选择保留这个代价是为了不破坏汉化包已有的译名。

8. **「恢复默认」这条链路的优先级依赖第三方模组的具体写法。**
   本模组用「通知型前缀提到 500 + 后缀兜底」扛住了 `QoL Unknown`（§4.4），但这套做法有个前提：对方的提前接管前缀必须真的调用 `Settings.DefaultSettings()`。**如果将来某个模组改成"自己造一份列表、根本不调用 `DefaultSettings()`"**，本模组的 `Attach` 就不会被触发，此时靠后缀兜底 `ForceReset` 仍然能把 32 项重置（它会自己调一次 `DefaultSettings()`），代价是那股"记忆值"要等到下一次打开设置页才被彻底清掉。这条不是缺陷，是如实说明兜底路径的能力边界。

9. **兼容垫片只兜异常，不修别人的 bug。**
   `Patches\PatchCompat.cs` 的 `[HarmonyFinalizer]` 挂在 `RecipeItem.DoesUseItemType` 上（§2 第 19 条）。它的能力边界要说清楚：① 它只把**这一条**方法抛出的异常转成「不满足该槽位」（`false`），不会去补 null、也不会改变原版判定结果——所以如果哪件材料真的取不到 `Stats`，界面上的库存计数会**偏低**而不是崩溃；② 它不影响原方法正常返回的路径，也不碰 Crafting Tweaks 的逻辑（对方下一次更新若自己修好了，这里就是一条永不触发的垫片）；③ 触发时写的那行 `[Compat] …` 带上物品 id、`Stats` 是否为 null、容器内每个液体 stack 的 id 与是否在 `Liquids.Registry` 里、槽位标识，是为了下一次复现时能直接定位到是哪一个物品/液体注册表缺项，而不是靠猜。
