### 2.1 `Patch_GetItemsForRecipe`（合成「快速选材」入口）

- 补丁类：`BalaurBohemianBroken.Patch_GetItemsForRecipe`（`Patches.cs:7-14`）
- 目标：`Recipe.GetItemsForRecipe`（`Patches.cs:9` 用 `nameof`），游戏侧真实签名为 `public List<Item> GetItemsForRecipe()`（`Recipe.cs:114`）
- 类型：**Prefix**，`public static bool Prefix(Recipe __instance, ref List<Item> __result)`
- 是否整体替换：**是**，`return false;`（`Patches.cs:12`）
- 方法体（`Patches.cs:11-12`）：`__result = CraftingLogic.GetItemsForRecipe(__instance, true); return false;`
- 优先级：无；异常保护：无

**装/不装的行为差异**：不装模组时，游戏按自身顺序遍历物品（`Recipe.cs:114-142`）：槽位匹配靠 `RecipeItem.GetMatchingItem`，**第一个满足条件的物品就被选中**，且只从「身上 + 10 米内的地面物品」里取，任何一个槽位找不到材料就 `return null`（即该配方判定为「当前做不了」，界面显示为不可用）。装模组后，选材交给 `CraftingLogic.GetItemsForRecipe(recipe, stop_on_null: true)`：所有可用物品先被拿去过滤、排序，再取「最想要的」那件（排序规则见第三节），因此**同一套材料下，模组会挑出不同（通常是更省、更不心疼）的那一件**，例如优先用地上散落的、品质更低的、耐久更差的同类材料；配方仍不可用的判定保留（`CraftingLogic.cs:145-147` 在 `best_item == null && stop_on_null` 时返回 null）。

1. 智力判定与惩罚段（`Patches.cs:107-128`）与游戏原版 `RecipeResult.cs:18-42` **逻辑等价**：

## 三、选材算法（`CraftingLogic.cs`）

### 3.1 静态开关（模组自己的字段）

### 3.2 入口：`GetItemsForRecipe`

`CraftingLogic.GetItemsForRecipe(Recipe __instance, bool stop_on_null)`（`CraftingLogic.cs:134-158`）：

1. `List<Item> allItemsThorough = BetterInventoryLogic.GetAvailableItems(true);`——**包含 10 米内可拾取的地面物品**（`Main.cs:33-47`），所以模组会「用脚边的材料」。
2. `allItemsThorough.RemoveAll(item => item.favourited);`——**收藏（favourited）的物品一律不参与选材**（与游戏原版 `RecipeItem.cs:29` 的 `!item.favourited` 一致，属于同一套语义的双保险）。
3. 逐个 `RecipeItem`：`Item best_item = GetBestItemForCraftingSlot(recipe_item, allItemsThorough.ToList());`（把列表复制一份，保证每个槽位在同一批候选里独立排序）。
4. `if (best_item == null && stop_on_null) return null;`——即 2.1/2.2 中 `stop_on_null` 的真假决定「整表失败」还是「塞一个空位」。
5. `items.Add(best_item);`
6. `if (best_item != null && recipe_item.destroyItem && !recipe_item.isLiquid) allItemsThorough.Remove(best_item);`——**会被销毁的非液体材料，从候选池里移除**，避免同一个槽位/多个槽位重复挑中同一件（原版是靠 `Recipe.cs:129-136` 的 list2 排除表实现同一目的；注意模组这一条只对「会被销毁」的材料生效，液体与不销毁材料仍可能被反复选中）。
7. `CraftingLogic.cs:133` 有一条注释，说明作者已验证「合成时的掉帧不是本模组造成的」。

### 3.3 `CanUseInRecipeSlot`——候选过滤（`CraftingLogic.cs:89-131`）

外层只有一个前置条件：

```csharp
if (!item.favourited && (!(item.id == recipe_slot.ignoredId) || recipe_slot.isLiquid))
```

即：**收藏品直接排除**；`ignoredId` 命中时排除，但**液体槽位例外**（液体槽位的 `ignoredId` 语义是「允许的口味白名单」而非黑名单）。

之后按液体/固体分流：

- **液体槽位**（`recipe_slot.isLiquid`，要求物品有 `WaterContainerItem`，`CraftingLogic.cs:92-111`）：
  - `specific` 槽位：要求 `component.AmountOf(recipe_slot.specificId) >= recipe_slot.minimumCondition`；
  - 非 specific：遍历 `component.stack` 的每个 `LiquidStack`，`Liquids.Registry.TryGetValue(liquidStack.liquidId, out liquidType)` 成功后，要求 `Item.GetQualityThatMeetsCriteria(recipe_slot.quality, liquidType.GetScaledQualities(liquidStack.amount)) != null`——即**液体按「换算品质」参与配方品质要求**。
- **固体槽位**（`CraftingLogic.cs:112-130`）：
  - **排除「有内容物的容器」**：`if (!item.TryGetComponent<Container>(out component) || component.itemCount <= 0)` 才继续（`itemCount` 的定义见 `Container.cs:22`，等于子物体数）。也就是**装了东西的背包/箱子不会被拿去当合成材料**，与游戏原版 `RecipeItem.cs` 的同款判断一致；
  - `specific` 槽位：`item.id == recipe_slot.specificId && item.condition >= recipe_slot.minimumCondition`；
  - 否则：`item.condition >= recipe_slot.minimumCondition && Item.GetQualityThatMeetsCriteria(recipe_slot.quality, item.Stats.qualities) != null`；
  - 都不满足 → `false`。

补充两条游戏侧对「消耗/不消耗」的规则（选材算法必须知道，否则会误解模组行为）：

- `minimumCondition` 是**耐久门槛**：`RecipeItem.minimumCondition` 默认 `0.9f`，`UseItem` 在 specific 槽位下是 `item.condition -= minimumCondition`（`RecipeItem.cs:118-176` 段）——即「按门槛扣耐久」而不是「整件消失」。
- `destroyItem`（默认 `true`）决定消耗方式：为真时 `UseItem` 会先把材料内部物品全部倒出（`container.UnloadAllItems()`）再 `DropItem` + `Destroy`；为假/液体时走 `CalculateDrainSingleLiquid` + `Drain` 的抽取路径。因此**模组只能影响「挑哪一件」，不能改变「消耗多少」**。

### 3.4 `GetBestItemForCraftingSlot`——最终挑中哪一件（`CraftingLogic.cs:160-177`）

```csharp
List<Item> candidates = ...; // 所有 CanUseInRecipeSlot(item, slot) 为真的物品
if (candidates.Count == 0) return null;
candidates.Sort((x, y) => CompareCraftingDesirability(x, y, slot));
return candidates.Last();
```

即：**过滤 → 用比较栈排序 → 取排序结果的最后一个**。

### 3.5 `CreateCraftingComparisonStack`——比较栈顺序（`CraftingLogic.cs:179-209`）

按**先进先出**（先入栈的比较器优先级更高，见 3.6）构造，顺序固定为：

| 顺序 | 比较器 | 开关 | 开关默认 |
| --- | --- | --- | --- |
| 1 | `ItemCompareOnFloor` | `prefer_on_floor` | 关（构造参数 `false`，见下） |
| 2 | `ItemCompareContainer` | `prefer_not_container` | 开（`true`） |
| 3 | `ItemCompareWearable` | `prefer_not_wearable` | 开（`true`） |
| 4 | `ItemCompareOnBody` | `prefer_on_body` | 关（`false`） |
| 5 | `ItemCompareQuality` | `prefer_high_quality` | 关（`false`） |
| 6 | `ItemCompareValue` | `prefer_low_value` | 开（`true`） |
| 7 | `ItemCompareCondition` | `prefer_low_condition` | 开（`true`） |

每个比较器的构造参数（`reverse`）就是上表第三列的 `false/true`，用途见 3.6。

### 3.6 比较机制：`CompareCraftingDesirability` + `ItemComparison`

`CompareCraftingDesirability(Item x, Item y, RecipeItem recipe_slot)`（`CraftingLogic.cs:211-219`）：**按栈顺序依次比较，返回第一个非 0 的结果；全部相等返回 0**。因为最终取 `candidates.Last()`，所以：

- 约定「更想要的排在后面」——比较器返回正数表示 `x` 比 `y` 更可取（`x` 排后、更可能被选中）。

`ItemComparison` 抽象基类（`CraftingLogic.cs:224-242`）提供反向机制：字段 `_reverse`、属性 `Reverse`、`protected int reverse_sign = 1;`，`Reverse` 的 setter 里 `reverse_sign = Reverse ? -1 : 1;`（构造时传入 `ItemComparison(bool reverse)`）。**约定：`reverse_sign` 必须显式乘进返回值才能翻转语义——漏乘就是 bug**（见第八节）。

各比较器判定规则：

| 比较器 | 行号 | 判定规则 |
| --- | --- | --- |
| `ItemCompareQuality` | `CraftingLogic.cs:252-261` | 先 `if (recipe_slot.quality == null) return 0;`，再按 `isLiquid` 分派到下面两个 |
| ├ `CompareSolids` | `CraftingLogic.cs:263-274` | 双方各取 `Item.GetQualityThatMeetsCriteria(recipe_slot.quality, item.Stats.qualities)`，**任一为 null 直接 `return 0`**；否则 `x_amount.CompareTo(y_amount) * reverse_sign` |
| └ `CompareLiquids` | `CraftingLogic.cs:276-313` | 无 `WaterContainerItem` 的一方直接 -1/1；specific 槽位比 `AmountOf(specificId)`；否则各自遍历 `stack`，把「换算品质的 amount」赋给 `x_amount`/`y_amount`，**命中 null 就 `break`**，最后比较两者 |
| `ItemCompareValue` | `CraftingLogic.cs:316-324` | `x.Stats.GetValue(x).CompareTo(y.Stats.GetValue(y)) * reverse_sign`（`GetValue` 逻辑见 `ItemInfo.cs:103-121`：基础价值 × 耐久 + 液体价值，液体部分上限 50） |
| `ItemCompareCondition` | `CraftingLogic.cs:326-334` | `x.condition.CompareTo(y.condition) * reverse_sign` |
| `ItemCompareContainer` | `CraftingLogic.cs:336-351` | 都有/都无 `Container` → 0；`x` 有而 `y` 无 → `-1 * reverse_sign`（`CraftingLogic.cs:345`）；`x` 无而 `y` 有 → `1 * reverse_sign`（`CraftingLogic.cs:348`）（配合 `reverse=true`，即「不是容器的更想要」）。**注意它读的是 `Item.container`（`Item.cs:66`，物品自身是不是一个容器），而不是「物品是否装在某个容器里」**
| `ItemCompareWearable` | `CraftingLogic.cs:353-370` | 取 `x.Stats.wearable` 与 `y.Stats.wearable` 判断，返回 `±1 * reverse_sign`（配合 `reverse=true`，即「不是穿戴物的更想要」） |
| `ItemCompareOnBody` | `CraftingLogic.cs:372-386` | 用 `StorageLogic.IsItemOnBody`：在身上返回 1，否则 -1（**未乘 `reverse_sign`**） |
| `ItemCompareOnFloor` | `CraftingLogic.cs:388-402` | 用 `StorageLogic.IsItemOnFloor`：在地上返回 1，否则 -1（**未乘 `reverse_sign`**） |

**由此得到玩家能感受到的实际选材偏好（默认设置下）**：优先用**地上的**（第 1 条比较器，权重最高）→ 其次优先**不是容器**的 → 再次优先**不是穿戴物**的 → 然后优先**不在身上**的（即背包/容器里的）→ 品质要求能被「更高换算品质」的材料满足时优先高品质 → 同等条件下优先**价值更低**的 → 最后优先**耐久更差**的（把好货留着自己用）。全部 7 个开关默认开启时，就是**「先捡地上的破烂，再动背包里的好货」**这一套。

### 4.2 总流程

```
AutoPickup(item, character)
   ├─ item.Stats.HasTag("noautopickup") → 直接 return（什么都不做）
   ├─ 不可穿戴 → AddItemToInventory(item) → 返回字符串"放哪了"（null 视作 "the floor"）→ storing_in.Add(...)
   └─ 可穿戴   → 同槽已有穿戴物先 DropItem 到地上 → WearWearable(item) → PlayerCamera.main.UpdateWearables()
```

`AutoPickup(Item item, Body character)`（`StorageLogic.cs:90-110`，注释注明「Based on `Body.AutoPickUpItem`」）：

1. `if (item.Stats.HasTag("noautopickup")) return;`（与游戏原版 `Body.cs:836-869` 的标签判断一致）；
2. **不可穿戴**：`string stored_in = AddItemToInventory(item); if (stored_in == null) stored_in = "the floor"; storing_in.Add(stored_in);`——**注意这里在成功路径上也会写入"the floor"**，即「入包失败 = 掉在地上」；
3. **可穿戴**：`Item wearableBySlotID = character.GetWearableBySlotID(item.Stats.wearSlotId); if (wearableBySlotID != null) character.DropItem(wearableBySlotID); character.WearWearable(item); PlayerCamera.main.UpdateWearables();`——**先脱旧的（丢地上）、再穿新的**；**但这条分支完全不写 `storing_in`**，也不弹提示（穿戴物不参与「存放」提示）。

`AddItemToInventory(Item item)`（`StorageLogic.cs:112-132`）：

1. `if (!store_in_containers_first && TryHoldItem(item) != -1) return "inventory";`——**默认设置是「先放容器」**，所以默认先跳到第 2 步；
2. `Container stored_in = TryStoreItem(item); if (stored_in != null) return BetterInventoryLogic.NameOrUnrecognized(stored_in.mItem);`
3. 再试一次 `TryHoldItem(item) != -1` → `return "inventory"`；
4. 全部失败 → `return null`。

作者注释自述这个返回值设计「a bit gross」——因为 `"inventory"` 与容器的显示名共用同一个 string 通道，**无法在类型上区分「手持槽位」与「容器」**。

`TryHoldItem(Item item)`（`StorageLogic.cs:134-144`）：

```csharp
Body p = PlayerCamera.main.body;
int? slot = p.FirstEmptySlot();
if (slot != null) { p.PickUpItem(item, slot.Value, true); return slot.Value; }
return -1;
```

`FirstEmptySlot()` 的真实签名是 `public int? FirstEmptySlot()`（`Body.cs:1748-1758`），`PickUpItem` 是 `public void PickUpItem(Item item, int slot, bool force = false)`（`Body.cs:1687-1708`）。

`TryStoreItem(Item item)`（`StorageLogic.cs:146-166`）：

```csharp
foreach (Item surfaceInventoryItem in p.GetSurfaceInventoryItems())
{
    Container c = surfaceInventoryItem.container;
    if (surfaceInventoryItem.container == null) continue;
    if (!c.CanHoldItem(item)) continue;
    candidates.Add(c);
}
if (candidates.Count == 0) return null;
candidates.Sort((x, y) => CompareContainerDesirability(x, y, item));

container.LoadItem(item);
return container;
```

关键点：候选来源是 `Body.GetSurfaceInventoryItems()`（`Body.cs:912-928`，**只含身上槽位物品与其容器、以及穿戴物与其容器**，不含容器内容的嵌套内容物）；调用的是 `Container.LoadItem(Item)`（`Container.cs:113-141`，返回 **void**，**不返回成功与否**）；按比较栈排序后取 `Last()`。

### 4.3 `storage_comparison_stack` 顺序与各比较器判定

`CreateStorageComparisonStack()`（`StorageLogic.cs:186-204`）按顺序入栈：`StorageCompareType` → `StorageCompareWeightReduction` → `StorageCompareMostFull` → `StorageCompareLargest` → `StorageCompareBestCondition`（分别对应 `compare_storage_type` / `compare_storage_reduction` / `compare_storage_full` / `compare_storage_capacity` / `compare_storage_best_condition` 五个开关，默认全开）。

`CompareContainerDesirability`（`StorageLogic.cs:206-213`）：与选材同构——取第一个非 0 的结果，最终取 `Last()`。

| 比较器 | 行号 | 判定规则 | 默认效果 |
| --- | --- | --- | --- |
| `StorageCompareType` | `StorageLogic.cs:221-235` | 容器的 `tagRestriction.Length > 0` 时用 `tagRestriction.Intersect(item.Stats.GetTags()).Any()` 判断「这个容器允许装这类东西吗」；双方相同 → 0；`x` 匹配 → 1，否则 -1 | 更「对口」的容器（如弹药袋装弹药）排后 → 优先选中 |
| `StorageCompareWeightReduction` | `StorageLogic.cs:237-241` | `x.encumberanceMult.CompareTo(y.encumberanceMult) * -1`，字段定义见 `Container.cs:10`（`encumberanceMult = 1f`） | 负重系数**更小**（减重更好）的容器排后 → 优先选中 |
| `StorageCompareMostFull` | `StorageLogic.cs:243-249` | `float x_space_left = x.maxWeight - x.GetHoldingWeight();` 然后 `x_space_left.CompareTo(y_space_left)` | 剩余空间**更小**（更满）的容器排后 → 优先选中（「先塞满一个再开下一个」） |
| `StorageCompareLargest` | `StorageLogic.cs:251-255` | `x.maxWeight.CompareTo(y.maxWeight)` | 容量**更大**的排后 → 优先选中 |
| `StorageCompareBestCondition` | `StorageLogic.cs:258-262` | `x.mItem.condition.CompareTo(y.mItem.condition)` | 容器自身耐久**更高**的排后 → 优先选中（`StorageLogic.cs:257` 留有 TODO 注释） |

`Container` 侧字段依据：`maxWeight`（`Container.cs:6`）、`maxWeightPerItem`（`Container.cs:8`）、`encumberanceMult`（`Container.cs:10`）、`mItem`（`Container.cs:12`）、`tagRestriction`（`Container.cs:20`）、`itemCount`（`Container.cs:22`）、`GetHoldingWeight()`（`Container.cs:77-88`，累加子物体 `totalWeight`）、`CanHoldItem(Item)`（`Container.cs:100-111`，要求 `item.totalWeight <= maxWeightPerItem` 且 `GetHoldingWeight() + item.totalWeight <= maxWeight`，`tagRestriction` 非空时还要求标签有交集）。

### 4.4 `IsItemOnBody` / `IsItemOnFloor`

```csharp
public static bool IsItemOnBody(Item item)  // StorageLogic.cs:173-179
    => !item.Stats.wearable && !item.rb.simulated && item.ParentContainer() == null;

public static bool IsItemOnFloor(Item item) // StorageLogic.cs:181-184
    => item.ParentContainer() == null && !IsItemOnBody(item);
```

- `ParentContainer()` 的真实签名是 `public Container ParentContainer()`（`Item.cs:105-112`），非 null 表示「这件东西正被装在一个容器里」。
- `item.rb` 是 `Item.rb`（`Item.cs:27`）；`rb.simulated == false` 在游戏里是「已被收进身体/背包」的标志（`Body.cs:1697` 的 `PickUpItem`、`Body.cs:1801` 的 `WearWearable` 都会置 false；`Body.cs:1740` 的 `DropItem` 会置 true）。
- 作者注释自己声明这两条判断不可靠：`IsItemOnBody`（`StorageLogic.cs:173-179`）标注「几乎肯定会导致漂浮物品之类的诡异 bug，因此显式排除 wearable 且不做『是否真的穿着』的检查」；`IsItemOnFloor`（`StorageLogic.cs:181-184`）标注「This isn't a great check」。
- 逻辑后果：一件**未穿戴的衣物类物品**（`Stats.wearable == true`）掉在地上时，`IsItemOnBody` 与 `IsItemOnFloor` **都会返回 false**。这会同时影响选材的第 1、4 条比较器（两者都返回 0，等于该维度弃权）。


### 5.1 静态开关

### 5.2 `FindBestBottle`——候选条件（`LiquidStorageLogic.cs:86-117`）

遍历 `PlayerCamera.main.body.GetAllItemsThorough()`，对每个带 `WaterContainerItem` 的物品（`WaterContainerItem` 定义见 `WaterContainerItem.cs:8`，**它不是 `Container` 的子类**）做四道过滤：

1. `if (liquid_container.SpaceLeft < liquid_amount) continue;`——剩余容量（`SpaceLeft => Mathf.Max(0f, Capacity - CurrentTotal)`，`WaterContainerItem.cs:51`）必须放得下这一份；
2. `if (!can_fill_new_bottles && liquid_container.CurrentTotal == 0) continue;`——`can_fill_new_bottles == false` 时**不允许动用空瓶**；
3. `bool has_stack = liquid_container.HasLiquid(liquid_id);`（`WaterContainerItem.cs:53`）、`int other_liquids = liquid_container.stack.Count(); if (has_stack) other_liquids -= 1;`——算出「瓶里除本液体外还有几种液体」；
4. `if (other_liquids > 0) { if (!can_stack_into_mixed) continue; if (!has_stack) continue; }`——瓶里已有别的液体时：**默认（`can_stack_into_mixed == false`）直接排除**；即使允许混装，**也要求瓶里已经含有本液体**（即「只往本来就装过这种液体的混合瓶里续」，不允许把新液体倒进异种液体瓶）。

通过全部过滤的瓶子进 `candidates`，然后 `candidates.Sort((x, y) => CompareLiquidContainerDesirability(x, y, liquid_id, liquid_amount)); return candidates.Last();`；空候选返回 `null`（`LiquidStorageLogic.cs:112-116`）。

### 5.3 三个比较器

`CompareLiquidContainerDesirability`（`LiquidStorageLogic.cs:76-84`）：取第一个非 0 结果（与前面同构）。

| 比较器 | 行号 | 判定规则 | 默认效果 |
| --- | --- | --- | --- |
| `CompareLiquidStacking` | `LiquidStorageLogic.cs:140-146` | `x.AmountOf(liquid_id).CompareTo(y.AmountOf(liquid_id))`（`AmountOf` 见 `WaterContainerItem.cs:82`） | 已经装了**更多**本液体的瓶子排后 → 优先选中（「把同一瓶灌满再换下一瓶」） |
| `CompareLiquidWeightRatio` | `LiquidStorageLogic.cs:148-163` | `x.item.Stats.weight / x.Capacity` 与 `y` 同式比较后 **`* -1`** | **满瓶重量比更低**（更划算）的瓶子排后 → 优先选中。作者注释说明：不考虑「液体不增重」的容器，水壶虽然不增重但储量很差，所以用比值衡量 |
| `CompareLiquidUnmixed` | `LiquidStorageLogic.cs:165-176` | 用 `x.stack.Count`（`HasLiquid(liquid_id)` 时减 1）比较后 **`* -1`** | 混装种类**更少**的瓶子排后 → 优先选中（这条只在 `can_stack_into_mixed == true` 时才被装上） |

### 5.4 `StoreLiquid`——实际灌装（`LiquidStorageLogic.cs:119-132`）

## 八、已知缺陷与限制

以下每条都是**直接在源码中看到**的问题，附证据行号与不合理的原因。

### ① `Dictionary.Add` 非幂等，重复调用 `LoadLanguage` 会抛异常

`Patches.cs:78` 用 `Locale.currentLang.other.Add(line.Key, line.Value)` 注入键，而 `Locale.currentLang.other` 的类型是 `Dictionary<string, string>`（`Language.cs:17`）。`Dictionary.Add` 遇到已存在的键会抛 `ArgumentException`，而这个 Postfix **没有 `try/catch`**（`Patches.cs:25-81`）。只要 `LoadLanguage()` 在同一次运行里被调用两次且 `currentLang` 没被替换（`Locale.cs:198-223` 里有多条 `return` 路径，某些路径不会重建语言对象），就会在设置界面无法显示模组项甚至更早的地方报错。**本条在源码层面是确凿的风险；当前 6 个语言包中相关键命中数为 0，因此是否可复现取决于运行时路径（未验证）。**

### ② 设置界面「重置为默认值」不会重置模组的 19 个开关

`Patches.cs:87-89` 是 `__result.AddRange(CraftingLogic.settings)` 等——把**模组静态字段持有的同一批 `Setting` 实例引用**塞进新列表。而游戏的 `SettingsMenu.ResetToDefault()`（`SettingsMenu.cs:35-41`）执行的是 `Settings.settings = Settings.DefaultSettings(); Settings.ApplyAll(); Settings.SaveSettings(); SelectTab(0);`：`DefaultSettings()`（`Settings.cs:20-573`）每次都 `new` 出原生项的**新实例**（所以原生项会回默认值），但模组项返回的仍然是**同一批老对象**，其 `value` 字段保持不变。结果：玩家点「重置为默认值」后，模组 19 项**保留玩家当前的选择**，与按钮的含义不符。

### ③ 整体替换 `RecipeResult.SpawnResult` 会影响其它模组

`Patches.cs:93-170` 是 Prefix + `return false`，且**没有 `[HarmonyPriority]`**。Harmony 的规则是：Prefix 返回 false 会跳过原方法，**同时跳过所有优先级更低/更晚注册的 Prefix**（Postfix 仍会执行）。于是：任何其它修改 `SpawnResult` 行为的模组（无论是前缀式加料还是替换式重写，只要优先级低于本模组）都会**静默失效**，且顺序取决于加载次序，表现为「随机某个模组不生效」。作者在 `Patches.cs:97-105` 自己注明这段代码是照抄反编译结果、并留下「若出兼容问题就改成 transpiler」的备忘，说明这一点属已知取舍而非疏漏。

### ④ `CompareLiquids` 的三个问题（`CraftingLogic.cs:276-313`）

- **`break` 过早退出**：遍历 `x_liquid.stack` 找换算品质时，`if (qual == null) break;`（`CraftingLogic.cs:299-300`，`y` 侧同构在 `CraftingLogic.cs:307-308`）会在遇到第一个不合格液体栈时**直接停止遍历**，而不是继续找后面的栈——结果取决于 stack 顺序，与「这瓶液体整体能不能满足品质要求」的直觉不符。
- **specific 分支同样漏乘 `reverse_sign`**：`CraftingLogic.cs:292-293` 直接 `return x_liquid.AmountOf(recipe_slot.specificId).CompareTo(y_liquid.AmountOf(recipe_slot.specificId));`，既没乘符号也没有品质换算。
- **取到的是「最后一个」匹配栈**：`x_amount`/`y_amount` 被循环反复覆盖，最终参与比较的是最后一次赋值的结果，而不是「最合适的那个栈」。
- **结果未乘 `reverse_sign`**（见 ⑥ 同类问题）。

### ⑤ 索引器访问 `Liquids.Registry` 可能抛 `KeyNotFoundException`

`CraftingLogic.cs:297` 与 `CraftingLogic.cs:305` 使用 `Liquids.Registry[liquid_stack.liquidId]` 直接索引；游戏原版在同类场景使用的是 `TryGetValue`（`RecipeItem.cs` 液体匹配段），模组自己的 `CanUseInRecipeSlot` 也是用 `Liquids.Registry.TryGetValue(...)`（`CraftingLogic.cs:97-99`）。**同一个文件里两种写法并存**，说明这里是笔误而非有意。一旦某个液体 id 不在注册表里（旧存档、其它模组注入的自定义液体），就会抛出异常；由于补丁没有 `try/catch`，异常会直接冒到 `GetItemsForRecipe` 的调用方（`PlayerCamera.cs:565/632/680`）。

### ⑥ 三个比较器忘记乘 `reverse_sign`（`Reverse` 开关形同虚设）

`ItemCompareOnBody`（`CraftingLogic.cs:372-386`）、`ItemCompareOnFloor`（`CraftingLogic.cs:388-402`）与 `CompareLiquids`（`CraftingLogic.cs:276-313`）直接返回 `1` / `-1` / 未乘符号的比较结果，而 `ItemComparison` 的设计（`CraftingLogic.cs:224-242`）要求所有返回值乘 `reverse_sign` 才能让 `Reverse = true` 生效。**当前行为正确纯属巧合**：这三处的构造参数传的都是「不反转」的值（`ItemCompareOnFloor(false)`、`ItemCompareOnBody(false)`，见 3.5），此时 `reverse_sign == 1`。一旦有人把构造参数改成 `true`、或新增一个 `Reverse = true` 的比较器，语义就会**静默反向**（不报错，只是选错东西）。这是一个埋着的坑，不是当前可见的 bug。

### ⑦ 装载不校验成功，提示会撒谎

`StorageLogic.cs:158-163`（核心调用在 `StorageLogic.cs:161`）：

```csharp
Container container = candidates.Last();
container.LoadItem(item);
return container;
```

`Container.LoadItem(Item)` 的真实签名是 `public void LoadItem(Item item)`（`Container.cs:113-141`）——**返回 void，且有三条静默失败路径**：装入的物品本身是「装了东西的容器」时 `DoAlert(...alertcontainerstacking)` 后不装载；容器自身已经被别人装着（尝试套娃）时 `DoAlert(...alertcontainerstackingalt)` 后不装载；`CanHoldItem` 失败或两者距离 ≥ 10f 时不装载（只有通过全部检查才真正 `SetParent` 并把 `item.rb.simulated = false`，`Container.cs:126-127`）。模组**无视这些失败**，直接 `return container`，于是返回值被写进 `storing_in`，最终提示玩家「Stored: 某个容器名」，而物品实际还在原地（或掉在地上）。这是「提示与事实不符」的确凿路径。

### ⑧ 提示文案硬编码英文（设置项文案同样是英文）+ `HashSet` 顺序不定 + 可能为空

- `StorageLogic.cs:170`：`PlayerCamera.main.DoAlert($"Stored: {stored_in}");`——`"Stored: "` 与 `"the floor"`（`StorageLogic.cs:99`）、`"inventory"`（`StorageLogic.cs:119/128`）**全部是硬编码英文字面量，没有走 `Locale`**。游戏自身的惯例是 `DoAlert(Locale.GetOther("..."))`（例如容器相关的 `alertcontainerstacking`，`Container.cs` 装载段），所以中文环境下这几段提示会**中英混杂**（容器名是中文的，前缀与 `inventory`/`the floor` 是英文）。这是模组处于未完成状态的直接证据。
- 同一根因的另一处表现：`Patch_LoadLanguage` 注入的 38 条设置文案**全是英文**（`Patches.cs:31-73`），且注入方式与语言无关（`Patches.cs:77-79` 无条件写入当前语言对象）。所以中文环境下，模组的 19 个开关在设置界面里**项名与说明都是英文**，而同一页面的游戏原生项是中文——这会让玩家以为模组「坏的」或「没适配」。模组目录下没有任何本地化文件（`PageImages\` 只有 5 张截图，`licence.txt` 是许可证），即**它从未做过本地化**。
- `storing_in` 是 `HashSet<string>`（`StorageLogic.cs:17`）：`String.Join` 出来的顺序**在多次运行/多次合成之间不保证稳定**，同一个容器被多次使用也只显示一次。
- `AutoPickup` 在「`noautopickup` 标签」与「可穿戴」两条分支上提前 `return`（`StorageLogic.cs:92-93`、`StorageLogic.cs:104-109`），**不写 `storing_in`**；此时若本次合成没有任何物品走存放路径，`Patches.cs:164-165` 仍会调用 `InformWhereStored()`，弹出 `Stored: `（空列表）——**提示存在但内容为空**。

### ⑨ `AutoPickup` 的 `character` 参数基本没用上

`StorageLogic.cs:90` 签名带 `Body character`，但只有可穿戴分支用它（`character.GetWearableBySlotID` / `character.DropItem` / `character.WearWearable`）；`TryHoldItem`（`StorageLogic.cs:136`）与 `TryStoreItem`（`StorageLogic.cs:147`）内部**硬编码** `PlayerCamera.main.body`。结果：这个 API 表面上接受任意角色，实际只能对**玩家自己**生效；若将来有其它模组想用它给 NPC 或第二个角色分配物品，会静默作用于玩家。

### ⑩ 临时瓶定时销毁

`Patches.cs:139-145`：找不到瓶子可灌时，现场 `Utils.Create("craftingbottle", ...)` 造一个临时瓶、灌好液体、走一次 `StorageLogic.AutoPickup`，然后 `Object.Destroy(gameObject, 300f)`。这个 300 秒与游戏原版一致（`RecipeResult.cs:64` 同为 300f），属于**继承行为而非模组新增**；但需要注意两点：(1) 若该临时瓶已被 `AutoPickup` 收进玩家容器，它**照样会在 300 秒后被销毁**，液体一起消失（与游戏原版相同的风险，模组把它带进了新的路径）；(2) 模组把「灌瓶失败」从一个「不产出」的结果变成了「产出一个 5 分钟后自毁的瓶子」，玩家观感差别很大。

### ⑪ 每次选材都做 10 米半径的物理查询，且每个配方各做一次

`CraftingLogic.cs:134-137` 调 `BetterInventoryLogic.GetAvailableItems(true)`，后者（`Main.cs:41`）会执行 `Physics2D.OverlapCircleAll(position, 10f, mask)`，并对每个命中做 `TryGetComponent<Item>` 与 `DoPickupCheck`（`Main.cs:42-45`，`DoPickupCheck` 内部还包含 `Linecast` 遮挡检测，`Body.cs:1656-1685`）。这与游戏原版同源（`Recipe.cs:119-126`），**不是模组新引入的开销**，但：

- `PlayerCamera.RefreshRecipeList()`（`PlayerCamera.cs:547-608`）会**对列表中每个配方各调一次** `GetItemsForRecipe()`（`PlayerCamera.cs:565-567`），而 `IngredientTextForRecipe`（`PlayerCamera.cs:632`）与 `RefreshCurrentlySelectedRecipe`（`PlayerCamera.cs:680`）又各再调一次 `GetItemsForRecipeThorough()`；每次调用都对全部可用物品重新枚举（`Body.GetAllItemsThorough()`，`Body.cs:871-910`）+ 一次 10 米物理查询 + 对每个槽位做一次 `List.Sort`（`CraftingLogic.cs:172`）。
- 合计是「**配方数 × 多次（物品枚举 + 物理查询 + 排序）**」。它不发生在每帧（仅在打开/刷新合成界面时，见第七节），但**物品与配方多时会造成一次性的明显卡顿**。这是复杂度问题，不是泄漏。（严格的开销数字未在真机测量——「开界面卡顿是否可感知」标注为**未验证**。）

### ⑫ `GetQualityThatMeetsCriteria` 传 null 会 NRE

`Item.GetQualityThatMeetsCriteria(CraftingQuality target, List<CraftingQuality> list)`（`Item.cs:223-226`）的实现是 `list?.FirstOrDefault(q => q.id == target.id && ...)`——**它只对 `list` 做了空保护，`target` 为 null 时会直接 NRE**。模组在 `CraftingLogic.cs:109` 与 `CraftingLogic.cs:125` 直接传入 `recipe_slot.quality`，没有判空（对比：`ItemCompareQuality.Compare` 在 `CraftingLogic.cs:255-256` 是做了判空的，说明作者知道这个字段可能为 null）。游戏原版 `RecipeItem.cs` 的对应匹配段有同样的前置假设，所以这更像是「沿用了原版的隐含契约」而非模组独有缺陷；但**模组把这段逻辑搬到了自己身上，就同时继承了这条风险**——一旦有配方槽位的 `quality` 为 null（例如其它模组或未来版本新增的配方），就会在选材时抛异常，而补丁没有异常保护。

### ⑬ 不构成缺陷、不要误报的一点

`Patches.cs:130` 的清空 `storing_in` 发生在智力判定之后——`case -3` / `default` 两条提前 `return false` 的路径（`Patches.cs:111-125`，`return false` 分别在 `Patches.cs:120` 与 `Patches.cs:125`）**不会重置集合**，但这两条路径也不会调用 `InformWhereStored()`（`Patches.cs:164-165`），所以**不会显示上一次的陈旧提示**；下一次成功合成时第 130 行会先重置。这里没有 bug。
