# 玩家自定义合成消耗偏好 — 可行性验证与方案设计

> 目标：为《Casualties: Unknown Demo》(Unity 2022.3.62f3 / BepInEx 5) 设计「玩家自定义合成消耗偏好」功能。
> 范围：**仅可行性验证 + 方案设计，不含任何 C# 实现代码**（下文引用的代码块全部是**现有源码原文**，作为证据）。
> 证据约定：游戏源码转储位于 `_GameSource\Assembly-CSharp\`，第三方模组源码位于 `cu-better-inventory-logic-1.0.5\`，DLL 结论来自 `decompile_external`。行号均为原文行号；带「空行已省略」的引用块只是去掉空行，字符未改。

---

## 0. 结论速览

- **一句话结论**：游戏原生设置系统只能注册「5 种固定控件类型（bool / int / float / dropdown / keybind）」的设置项并追加到已有标签页（或借 CUCoreLib 追加**新标签页**）；**不能新增控件类型**，不能做拖拽排序、任意长度规则表等自定义 UI，也不能为自定义类型持久化。
- **推荐方案**：**方案 A（权重数值）+ 方案 B1（原生 Dropdown 表达排序）混合** —— 全部使用原生控件类型，因此能同时拿到原生菜单、原生 `settings.json` 持久化与原生本地化键；规则表（方案 C）退化为「JSON 文件编辑 + 菜单内只读展示」。
- **最大技术限制**：① `SettingsMenu.SelectTab` 遇到未知 `Setting` 子类时 `g` 保持 null 直接 NRE（`SettingsMenu.cs:57` `GameObject g = null;` / `:59-143` 的 if-else 只覆盖 5 个原生类型 / `:145` `g.transform.GetChild(0)`）；② `Settings.LoadSettings` 的类型分派没有 else 分支，自定义类型值永远读不回来（`Settings.cs:621-640`）。

### 1.1 `Setting` 基类有哪些成员？分组与顺序由什么决定？

- `SettingCategory` 共 5 个值：`Video, Audio, Game, Input, Language`（`Setting.cs:5-12`）。**`Language` 类别没有任何原生 Setting**：`Settings.DefaultSettings()` 只产出 Video/Audio/Game/Input 四类（`Settings.cs:20-573`），语言页由 `SettingsMenu` 单独用 `Locale.GetAllLanguages()` 生成（`Locale.cs:170-196`）。

```csharp
public static T Get<T>(string name) where T : Setting   // Settings.cs:588-603（空行已省略）
{
    EnsureLoaded();
    Setting setting = settings.Find(s => s.name == name);
    if (setting == null) { Debug.LogError("Setting '" + name + "' not found."); return null; }
    if (!(setting is T result)) {
        Debug.LogError("Setting '" + name + "' is of type " + setting.GetType().Name + ", not " + typeof(T).Name);
```

- **`DefaultSettings()` 是「进程内只建一次」还是「每次开菜单重建」？** —— `SettingsMenu.OpenMenu` 不调用它（`SettingsMenu.cs:22-28`）；它在 `LoadSettings`（`Settings.cs:608`）与 `ResetToDefault`（`SettingsMenu.cs:35-41`）里被调用。因为 `initialized` 只在成功读到文件后置 true（`:648`），文件不存在时 `LoadSettings` **提前 return（`:609-613`）且不调用 `ApplyAll`**，所以首次运行会再走一遍。**净效果：每个进程内基本只建一次；点「重置」会整体重建。**
- `ApplyAll()`：遍历全部 setting 调 `Apply()`（`Settings.cs:652-658`）。
- `SaveSettings()`：`JsonConvert.SerializeObject(list, Formatting.Indented)` 写 `persistentDataPath + "/settings.json"`，元素是 `{ name, GetValue() }`（`Settings.cs:660-673`；保存时机＝关菜单 `SettingsMenu.cs:215-219`、重置 `:35-41`）。
- **实际落盘位置（本机实测）**：`C:\Users\chris\AppData\LocalLow\Orsoniks\CasualtiesUnknown\settings.json`，格式为 `[ { "name": "reswidth", "value": 3200 }, { "name": "fullscreen", "value": true }, ... ]`（共 510 行）。
- `SettingSaveData`：`[Serializable] public class { public string name; public object value; }`（`SettingSaveData.cs:3-8`）。

**结论**：用原生 5 种类型注册的设置项 → **免费持久化到 `settings.json`**；自定义 `Setting` 子类 → **值永远读不回来**（`Settings.cs:621-640` 无 else 分支），必须自己存（BepInEx `ConfigFile` 或自建 JSON）。

### 1.5 本地化通道，以及本机汉化模组会不会覆盖

- 键规则（全部来自 `SettingsMenu.cs`）：标题 `"gameset" + setting.name`（`:145`）；提示描述 `"gameset" + setting.name + "dsc"`（`:146-152`，`UITooltip{skipLocale = true; ...}`）；下拉选项 `"gameset" + setting.name + text`（`:104-110`）。
- 查不到就**原样返回 key**（`Locale.cs:103-108`）→ 未翻译时菜单显示 `gamesetprefer_on_floor` 这类键名。
- `Locale.LoadLanguage()` 每次调用都重新反序列化出一个全新的 `currentLang`（`Locale.cs:198-223`，`other` 字典为空）→ **Postfix 注入是安全且幂等的**。注入请用**索引器** `Locale.currentLang.other[key] = value`，不要用 `Dictionary.Add`（对照 `Patches.cs:29-79` 的 `.Add`，同键会抛 `ArgumentException`）。
- **本机汉化模组 `A.Multi_Mod.Chinese.Localization.dll` 实测结论**：它确实对 BetterInventoryLogic 有专门模块——`A.Multi_Mod.Chinese.Localization.Mods.CraftingLogic.CraftingLogicModule`，`private const string CraftingLogicGuid = "com.balaur.BetterLogic";`，且用 `Chainloader.PluginInfos.ContainsKey("com.balaur.BetterLogic")` 做存在性探测（**未加载该插件时整个模块直接 return，不注册任何东西**）。它做三件事：
  1. `Locale.LoadLanguage` 的 **`priority = 200` Postfix** `LoadLanguageReMergePostfix`，把 `CraftingLogicLocales.Others` 用**索引器** `currentLang.other[text] = value` 合并；
  2. 对 `StorageLogic.AutoPickup` / `StorageLogic.AddItemToInventory` 挂字符串字面量 Transpiler；
  3. `TextTranslator.Register("alert", ..., prepend: true)` 注册弹窗格式。
- **它会不会覆盖 `gameset*`？不会。** 在该 DLL 内做字符串扫描：`"gameset"` 字面量命中 **0** 次（仅有自身字段名 `GamesetKeys`）、`prefer` / `Prefer` / `Floor` / `Condition` 命中 **0** 次 → 它既不含也不构造 BetterLogic 的设置键。
- 但要注意 **priority 200 的语义**：同键冲突时它的 Postfix 后跑、以它为准（**推断**：Harmony Postfix 按优先级由低到高执行）。我们的键只要唯一（例如统一加 `bcl_` 前缀）就不会被覆盖。
- 本机另有外部 JSON 翻译表的先例：`BepInEx\plugins\KrokMPChineseSupplement\translations.zh-CN.json` 用 `gameset<设置名>` 作键翻译第三方模组（KrokMP）的设置项（例：`"krokosha_coop_gamesetkrokosha_coop_carry": "多人游戏：搬运"`）→ 说明「JSON 键表」也是本机玩家生态里已被接受的分发方式。
- 参考实现：CUCoreLib 的 `RegisterLocale` 注册的正是这四组键 —— `LocaleRegistry.Register(LocaleCategory.Other, "gameset" + Id, Label)`、`"gameset" + Id + "dsc"`、以及 dropdown 的 `"gameset" + Id + choice.Key`（另有 `LocaleCategory.Option` 一组）。

## 2. 方案设计

### 方案 A：7 个开关 → **权重数值**（加权打分替代字典序）

**① 玩家能表达什么**
「地面上的东西优先」有多重要、「优先低价值」有多重要……每个维度给 0~10 的权重；可一键切换「严格优先级（近字典序）」与「加权求和（可互相抵消）」。例如把「保新品」拉满、「地面优先」降到 1，就能实现「不惜用箱子里全新的刀，也不用地上那把快断的」。

**② 数据结构与设置项清单（全部原生类型 → 自动持久化）**

| 设置项 name | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `bcl_mode` | `SettingDropdown` | `0`（严格优先级） | choices：`["strict","weighted"]` |
| `bcl_w_floor` | `SettingFloat` | 权重对应现状：入栈次序第 1 | 0~10，`min=0 max=10` |
| `bcl_w_notcontainer` | `SettingFloat` | 第 2 | 同上 |
| `bcl_w_notwearable` | `SettingFloat` | 第 3 | 同上 |
| `bcl_w_onbody` | `SettingFloat` | 第 4 | 同上 |
| `bcl_w_quality` | `SettingFloat` | 第 5 | 同上 |
| `bcl_w_value` | `SettingFloat` | 第 6 | 同上 |
| `bcl_w_condition` | `SettingFloat` | 第 7 | 同上 |
| `bcl_strict_tiebreak` | `SettingDropdown` | `0` | 平分时用哪条兜底：`["condition","value","quality"]` |

- 默认值设计原则：**把 7 个权重设成 «1、0.5、0.25、…» 这样的指数递减**，或让 `bcl_mode = strict` 时**忽略权重、完全按权重降序还原现有入栈顺序** → 「默认行为与现在（BetterInventoryLogic 默认值）一致」，避免改变老玩家的手感。
- 打分算法（**不实现，只描述**）：`score(item, slot) = Σ weight_i × normalize_i(item, slot)`，各维度先用现有比较器的语义做**单物品标量**化：品质 → `Item.GetQualityThatMeetsCriteria(slot.quality, item.Stats.qualities).amount`（`Item.cs:223-226`）、价值 → 负 `Stats.GetValue(item)`、耐久 → 负 `item.condition`、位置/是否容器/是否穿戴 → 0/1（`ItemCompareContainer`/`ItemCompareWearable` 用 `x.Stats.wearable`，`ItemCompareOnBody`/`ItemCompareOnFloor` 用 `StorageLogic.IsItemOnBody/IsItemOnFloor`）。

**③ 与游戏原生设置系统的契合**
- 注册：`[HarmonyPatch(typeof(Settings), nameof(Settings.DefaultSettings))] Postfix` 里 `__result.AddRange(我们的 List<Setting>)`（与 `Patches.cs:83-91` 同款），全部用 `SettingFloat/SettingDropdown` + `category = Setting.SettingCategory.Game` → 出现在「游戏」标签页底部（顺序证据 `SettingsMenu.cs:51-56` + `:153-155`）。
- 持久化：`SettingFloat`/`SettingDropdown` 都在 `Settings.LoadSettings` 的分派表内（`Settings.cs:621-640`）→ 免费存进 `settings.json`。
- 本地化：为每个 name 注入 `gamesetbcl_w_floor` / `...dsc`，dropdown 另加 `gamesetbcl_mode` + `strict` / `weighted` 三个键（键规则见 `SettingsMenu.cs:145`、`:104-110`）。
- 生效：`apply = delegate { ... 重算权重缓存 ... }`，并让选料走我们的打分；挂点二选一 ——（i）Prefix 挂 `CraftingLogic.CompareCraftingDesirability(Item, Item, RecipeItem)`（`:211`）返回 `false` 给出加权比较值；（ii）若（i）不生效，改挂 `CraftingLogic.GetBestItemForCraftingSlot(RecipeItem, List<Item>)`（`:160`）整体接管「排序取末位」。

**④ 风险与实现成本**
- **JIT 内联风险（最大的不确定性）**：`GetBestItemForCraftingSlot` 里的 lambda 可能把 `CompareCraftingDesirability` 内联进已编译代码，导致 Harmony 补丁不生效 → 缓解：插件加载时**尽早**打补丁；`CraftingLogic.CompareCraftingDesirability` 是 `public static`（`:211`），若实测无效则退到挂 `GetBestItemForCraftingSlot`。**需实测确认**。
- **并列不稳定**：`List.Sort` 不稳定（`:160-177`）→ 权重全 0 或分数相等时结果随机；必须提供确定性兜底（`bcl_strict_tiebreak`）+ 建议在比较器里追加唯一键（如 `item.GetInstanceID()`）。
- **归一化尺度**：品质 amount、价值（int）、耐久（0~1）量级不同，权重语义会被量级淹没 → 必须归一化，这是实现成本的主要来源。
- 成本：中等（无自定义 UI，无自定义持久化；核心成本在打分与归一化）。

**⑤ 做不到的部分**
- **做不到「任意排序」**：权重是标量加法，无法表达「品质优先于价值，但价值优先于耐久」这类**非传递/带结构的优先级**（原因：加权和天然可交换，`CompareCraftingDesirability` 的输入只有两个 `Item` 和一个 `RecipeItem`，`:211`）。
- **做不到「按配方不同给不同权重」**：单个 Setting 是全局值，若要做「切肉一套、装药一套」必须引入方案 C 的规则表。

### 方案 B：**可排序的偏好列表**（玩家决定优先级顺序）

拆成两个子方案：B1 用原生控件近似，B2 用自建 GUI 做到真拖拽。

#### 方案 B1（推荐）：用 N 个 `SettingDropdown` 当「优先级槽」

**① 玩家能表达什么**：一条**有序的**偏好链 —— 「第 1 优先考虑：品质；第 2：地面；第 3：低价值；第 4~7：不用」。等价于让玩家手动排列那 7 个比较器，正好落实 `Main.cs:14-21` 的 `// TODO: Allow users to organize the stack themselves.`。

**② 数据结构与设置项清单**

| 设置项 name | 类型 | 默认值 | choices |
|---|---|---|---|
| `bcl_slot1` … `bcl_slot7`（7 项） | `SettingDropdown` | 依次 `0,1,2,3,4,5,6`（还原现有栈序） | `["none","on_floor","not_container","not_wearable","on_body","high_quality","low_value","low_condition"]` |

- 解析规则（描述）：按 slot1→slot7 顺序收集非 `none` 的比较器，去重后构建 `crafting_comparison_stack` 的替代序列；缺项自动补齐到 7 项（保证与旧行为向后兼容）。
- 数据落地：**7 个 `SettingDropdown` 的 `value`（int）天然进 `settings.json`**（`Settings.cs:621-640`），不需要额外文件；`choices` 是 `string[]`（`SettingDropdown.cs:5`），选项文案由 `gameset<name><choice>` 键本地化（`SettingsMenu.cs:104-110`）。

**③ 契合方式**：与方案 A 完全相同的注册通道（`Settings.DefaultSettings` Postfix，`Patches.cs:83-91` 先例）；因为用的是原生 `SettingDropdown`，**菜单不会崩**（`SettingsMenu.cs:104-110` 有对应分支），且拿到原生持久化与本地化。

**④ 风险与成本**：成本**低**（7 个 dropdown，无自定义 UI）。风险：① 7 个下拉占屏空间大（每行都按 `sizeDelta.y` 递增排布，`:153-155`，7 行会明显加长「游戏」页）；② 玩家可表达的是**排列**而非严格「拖拽手感」；③ 重复选择需要去重逻辑（两个 slot 选同一项）——**未确认**游戏是否对 dropdown 重选项做任何限制（源码中无此逻辑，需我们自己解析时处理）。

**⑤ 做不到的部分**：**做不到真正的「拖拽排序」交互**。原因（源码证据）：自定义控件类型会在 `SettingsMenu.SelectTab` 里触发 `NullReferenceException`（`:57` 置 `g = null`，`:59-143` 无匹配分支，`:145` 直接访问 `g.transform`）；而 Prefix 整体替换 `SelectTab` 会连带跳过 CUCoreLib 的 `[HarmonyPostfix]`（`CUCoreLib.Patches.SettingsMenuSelectTabPatch`）等其它模组的 Postfix —— 代价过大。

#### 方案 B2（可选增强）：自建 GUI 面板做真拖拽

**① 玩家能表达什么**：鼠标按住偏好项上下拖到任意位置，实时预览顺序。

**② 数据结构**：顺序串（例如 `"high_quality,on_floor,low_value"`）—— **不是原生类型**，必须存到 **BepInEx `ConfigFile`** 或自建 JSON（原因：`Settings.cs:621-640` 的分派表不认自定义类型，`string` 也不是原生 Setting 类型）。

**③ 所需 API（全部已验证存在）**
- 打开入口：自己的 `SettingKeybind`（原生类型，`SettingKeybind.cs:5`，通过菜单可绑定按键）或复用一个已有按钮；
- 面板容器：`Utils.Create(string id, Transform parent)`（`Utils.cs` 两重载之一，`SettingsMenu.cs:22-28` 用法先例）克隆 `Special/SettingsMenu`，或直接克隆 `SettingsMenu.instance.content` 里的行预制体 `Special/GameSettingDropdown`；
- 布局：`RectTransform.anchoredPosition/sizeDelta`（`SettingsMenu.cs:153-155`、`:180` 先例）；
- 滚动：`ScrollRect`（`PlayerCamera.cs:347` 先例；CUCoreLib 的扩展器也自己实现了滚轮滚动与 `GetMaxScroll`）；
- 拖拽：`IBeginDragHandler/IDragHandler/IEndDragHandler` + `PointerEventData`（游戏程序集已引用 `UnityEngine.EventSystems`：`UIHoverDescription.cs:1-10`）；
- 遮挡判断：`UIUtil.GetEventSystemRaycastResults()` / `UIUtil.IsPointerOverUIElement`（`UIUtil.cs:25-36`、`:9`）；
- 音效：`PlayerCamera.PlayUISound("miniClick")`（`SettingsMenu.cs:185`）。

**④ 风险与成本**：成本**高**（自绘行、拖拽排序、滚轮、输入冲突、存档时机全要自己处理）；与游戏 UI 风格一致性需要手工调参；属于「能做但性价比低」的部分。

**⑤ 做不到的部分**：**做不到「把它塞进原生设置菜单」**（同 B1 的 NRE 证据）→ 只能做成**独立面板**（例如从自己的按键打开），游戏原生设置 UI 内看不到它。

### 方案 C：**按性质/物品类别的精细化偏好表**（规则表）

**① 玩家能表达什么**
带条件的偏好，例如：
- 「配方需要用 `cutting` 品质时，优先消耗品质**最低**的刀（低品质刀也能切，别用好的）」；
- 「`food`/`fruit` 类物品永远不要用于合成」；
- 「`medicine` tag 的物品优先消耗耐久最低的」；
- 「优先用 `trash` category 里的东西」。

**② 数据来源（全部已核实）**
- 物品品质：`ItemInfo.qualities`（类型 `List<CraftingQuality>`；MCP `list_fields ItemInfo` 确认字段存在），`CraftingQuality{ public string id; public float amount; }`，且**品质 id 是字符串**，本机游戏数据实测共 **11 个**：`cutting, dressing, firestarter, flammable, foliage, hammering, heatsource, meat, nails, produce, rippable`（`Item.cs` 内 `new CraftingQuality("...")` 去重统计）。
- 物品 tag：`ItemInfo.tags`（`ItemInfo.cs:75`）→ `SetTags()` 与 `public string[] GetTags()`（`ItemInfo.cs:141-144`，实际签名经 MCP 确认：`GetTags()`、`HasTag(String)`）；`Container.cs:106` 使用 `item.Stats.GetTags()` 证明 `Item.Stats` 就是 `ItemInfo`。**tag 实测 14 个**：`antiseptic, backflip, battery, belttool, bullet, cangetwet, dressing, fruit, gun, medicine, noautopickup, placeable, tool, water`。
- 物品类别：`ItemInfo.category`（**实测 10 个**：`container, custom, drug, food, medical, tool, trash, unobtainable, utility, water`）。
- 价值/耐久：`ItemInfo.GetValue(Item)`、`ItemInfo.DefaultValue()`（MCP `list_methods ItemInfo`）、`Item.condition`。
- 配方侧条件：`RecipeItem{ specific, specificId, isLiquid, quality(CraftingQuality), minimumCondition=0.9f, destroyItem=true, ignoredId }`（`RecipeItem.cs:6-18`）；匹配判定 `Item.GetQualityThatMeetsCriteria(质量, 列表)`（`Item.cs:223-226`）与 `Item.HasCommonQuality`（`:228-231`）；消耗量 `item.condition -= quality.amount / qualityThatMeetsCriteria.amount`（`RecipeItem.cs:163-165`）。

**③ 数据结构与设置项清单**

规则表本身（JSON，自管文件，例：`BepInEx\config\OptimisedCraftingSystem\rules.json`）字段建议：`{ "when": {"qualityId": "cutting", "itemTag": "tool", "category": "medical"}, "prefer": "low_quality", "weight": 3 }`，`prefer ∈ {low_quality, high_quality, low_value, high_value, low_condition, on_floor, not_container, not_wearable, on_body}`。

菜单内只暴露**少量原生开关/档位**（用于开关与选预设）：

| 设置项 name | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `bcl_rules_enabled` | `SettingBool` | `true` | 是否启用规则表 |
| `bcl_rules_preset` | `SettingDropdown` | `0` | choices：`["off","cautious","salvage","custom"]` 预设档（`custom` = 用 JSON） |
| `bcl_rules_strict_quality` | `SettingFloat` | `1` | 「同 tag 内按品质升序」的权重强度 |

**④ 契合方式**：设置项仍走 `Settings.DefaultSettings` Postfix + 原生类型（持久化/本地化免费）；**规则表内容**走自管 JSON（原因：原生设置系统只有 5 种标量控件，表达不了变长表；且自定义类型不持久化，`Settings.cs:621-640`）。编辑体验：菜单里给 `bcl_rules_preset` 选 `custom`，玩家用文本编辑器改 JSON；可选地在自建 GUI（方案 B2 的基础设施）里做成表格。

**⑤ 风险与成本**：成本**中高**（规则解析、匹配、冲突消解、缓存）；**规则冲突**需要确定性求解顺序（建议：更具体的条件优先，同具体度按 JSON 序号）；**性能**：选料发生在每次排序比较的循环里（`CraftingLogic.cs:160-177`），规则匹配必须预建 `tag → 规则` 字典缓存，否则每次比较都 `Split`/`FirstOrDefault` 会明显掉帧（`ItemInfo.SetTags()` 只在初始化时拆分，说明作者也走缓存路线）。

**⑥ 做不到的部分**：**做不到「在游戏原生设置菜单里编辑规则表」**。原因：没有任何文本输入类 `Setting`（`Setting.cs:5-12` 只有 5 个类别，全部具体类见 §1.2），而新增控件类型会让 `SelectTab` NRE（`SettingsMenu.cs:57`/`:145`）。

## 4. 推荐方案与落地步骤（不写代码，只写步骤）

**推荐：A + B1 混合的「一个模式开关 + 一套排序槽 + 一组权重」。**
理由：两者都只用原生控件类型，因而同时满足「进原生菜单」「原生持久化」「原生本地化键」三条；B1 覆盖「我要改顺序」的诉求（也是上游作者的 TODO），A 覆盖「我要调强弱」的诉求；B2/C 作为可选增强，避免在自定义 UI 上过早投入（NRE 与自绘成本双重风险）。

**落地步骤（每步都以「可验证」为完成标准）**

1. **前置验证（必须先做，决定后续路线）**：新建 `OptimisedCraftingSystem` 模组工作区（独立目录、唯一 `BepInPlugin` GUID，不占用 `com.balaur.BetterLogic`），先打两个探针：① `Settings.DefaultSettings` Postfix 追加一个 `SettingBool`，确认它出现在「游戏」页底部且写进 `settings.json`；② `CraftingLogic.CompareCraftingDesirability` Prefix 打印调用日志，确认补丁**真的会被调用**（这一步验证 JIT 内联风险，未通过就改挂 `GetBestItemForCraftingSlot`）。
2. **确定挂点与优先级**：确认与 `CraftingTweaks.dll`（`GetItemsForRecipe`×2）、`QoL Unknown.dll`（×3）的 Prefix 关系（用 BepInEx 日志 + `HarmonyPriority`），把我们的逻辑放在 `CraftingLogic` 之后、避免与它争抢 `Recipe.GetItemsForRecipe`。
3. **实现 B1 排序槽**：7 个 `SettingDropdown`（name 统一 `bcl_slot1..7`，`category = Game`），默认值还原现有栈序；解析+去重+补齐后生成比较器序列，替换 `crafting_comparison_stack` 的构建来源。
4. **实现 A 权重模式**：`bcl_mode`（strict/weighted）+ 7 个 `SettingFloat` 权重；strict 模式下忽略权重并严格按权重降序还原为栈序。
5. **打分与归一化**：按 §2 方案 A ② 的维度取值（品质用 `Item.GetQualityThatMeetsCriteria`，价值用 `Stats.GetValue`，位置用 `StorageLogic.IsItemOnBody/IsItemOnFloor`），**归一化到同一量级**，并加确定性兜底（分数相等时按耐久→价值→品质）。
6. **本地化**：在 `Locale.LoadLanguage` 的 Postfix 里用**索引器**注入 `gamesetbcl_*`、`gamesetbcl_*dsc`、以及每个 dropdown 的 `gamesetbcl_<name><choice>` 键（键规则见 `SettingsMenu.cs:145`、`:104-110`；用索引器而非 `.Add`，对照 `Patches.cs:29-79`）。中文文案与 `KrokMPChineseSupplement/translations.zh-CN.json` 风格保持一致的 JSON 键表，便于分发。
7. **可选增强**：C 的规则表先做 JSON（含 `bcl_rules_enabled`/`bcl_rules_preset` 两个原生设置项做开关），跑通后再考虑 B2 的自建拖拽面板。
8. **验收**：① 默认配置下选料结果与 BetterInventoryLogic 原版一致（回归基线）；② 改排序槽后消耗顺序随之变化；③ 重启游戏后设置保持（`settings.json` 复查）；④ 切换中英文后菜单文案正确；⑤ BepInEx 日志无 `NullReferenceException` / `Setting '...' not found`。
