## 0. 结论速览

1. 「性质」= `CraftingQuality { string id; float amount; }`（`CraftingQuality.cs:1-25`），`amount` 对**固体**是「该物品身上性质的点数」，对**液体**是「每 mL 的点数」（`LiquidType.cs:30-38`）。
2. 物品性质表是**静态数据**，只在 `Item.SetupItems()`（`Item.cs:233-6976`）里用对象初始化器写入 `ItemInfo.qualities`；运行期**没有任何代码修改它**（全树 grep `qualities` 只有初始化器写入 + 6 处读取，见 §A.2）。
3. 配方的「需求侧」全在 `RecipeItem`：`quality / minimumCondition / specific / specificId / isLiquid / destroyItem / ignoredId`（`RecipeItem.cs:6-18`）。`specific` **不是写出来的**，是 `SetUpRecipes()` 末尾由 `specificId` 派生（`Recipes.cs:4421-4432`）。
4. 消耗量公式（关键，§A.5）：
   - 固体非 specific：`item.condition -= quality.amount / q.amount`（**比例**，`RecipeItem.cs:163-165`）
   - 固体 specific：`item.condition -= minimumCondition`（**绝对值**，`RecipeItem.cs:159`）
   - 液体非 specific：`mL = quality.amount / 该液体每 mL 密度`（`RecipeItem.cs:141,145`）
   - 液体 specific：`mL = minimumCondition`（`RecipeItem.cs:149`，未写时默认 **0.9**，见 §A.5 的 morphine 陷阱）
5. 游戏里实际只存在 **18 个性质 id**（§B），其中只有 **6 个**（water / disinfectant / blood / opiate / fat / condiment）由液体提供，其余 12 个由固体物品提供；**没有任何性质 id 既被固体也被液体提供**。
6. 采集材料候选的运行时入口：`Body.GetAllItemsThorough()`（`Body.cs:871`）+ 脚下 10 单位内 `Physics2D.OverlapCircleAll(...).DoPickupCheck(..., noAlerts:true)`（`Recipe.cs:118-126`）。

## A. `CraftingQuality` 的完整机制

### A.1 类定义（全文 25 行）

```csharp
// CraftingQuality.cs:1-25
public class CraftingQuality
{
	public string id;
	public float amount;
	public string LocaleName => Locale.GetOther("cq" + id);
	public CraftingQuality(string id, float amount) { this.id = id; this.amount = amount; }
	public CraftingQuality(string id) { this.id = id; amount = 1f; }
	public static implicit operator CraftingQuality(string str) { return new CraftingQuality(str); }
}
```

要点：
- **显示名走 `Locale.GetOther("cq" + id)`**；`Locale.GetOther` 找不到键时**直接返回原字符串**（`Locale.cs:103-108`），所以自定义 id 只会显示成 `cqfoo`，不会抛异常。
- 单参构造与隐式字符串转换都让 `amount = 1f`。配方里两种写法都存在：`quality = "hammering"`（`Recipes.cs:977`）与 `quality = new CraftingQuality("hammering", 4f)`（`Recipes.cs:767`）。
- **没有重写 `Equals`/`GetHashCode`** → `Recipes.QualityExamples`（`Recipes.cs:18-36` 的 `Dictionary<CraftingQuality,string>`）是按**引用**比较的，所以原版 UI 用谓词 `FirstOrDefault` 而不是字典查找（`PlayerCamera.cs:656`）。模组要用这个字典时必须照做。

### A.3 液体性质的特殊之处

```csharp
// LiquidType.cs:28-38
public List<CraftingQuality> qualities = new List<CraftingQuality>();
public List<CraftingQuality> GetScaledQualities(float ml)
{
	List<CraftingQuality> list = new List<CraftingQuality>();
	foreach (CraftingQuality quality in qualities)
	{
		list.Add(new CraftingQuality(quality.id, quality.amount * ml));
	}
	return list;
}
```

**结论：液体 `qualities` 里的 `amount` 是「每 mL 的点数（密度）」**，`GetScaledQualities(ml)` 返回「这一份 ml 实际提供的总点数」。证据与推论：

- 代码只做 `quality.amount * ml`，是纯线性缩放，没有任何 `/1000` 或百分比约定。
- 需求侧比较的就是「总量」：`GetQualityThatMeetsCriteria(quality, value.GetScaledQualities(item2.amount))`，判据是 `q.amount >= target.amount`（`RecipeItem.cs:50`、`Item.cs:225`），即 `密度 × 液量 ≥ 配方要求`。
- 数值自洽：水密度 `1f`（`Liquids.cs:29`），配方 `titaniumslab` 要 `water 100f`（`Recipes.cs:763`）→ 100 mL 水；`milk` 配方要 `water 470f`（`Recipes.cs:3622`），牛奶密度 `0.5f`（`Liquids.cs:302`）→ 需 940 mL 牛奶（牛奶容器容量 1000 mL，成立）。
- 反直觉案例：芬太尼液体密度 `opiate 40f`（`Liquids.cs:264`），所以只要 1.25 mL 就能满足 `opiate 50f`（`Recipes.cs:2885`）。
- 反面：`opium` 液体密度只有 `0.4f`（`Liquids.cs:139`），要满足 `opiate 50f`（`Recipes.cs:3342`）需要 125 mL。

### A.4 需求侧：`RecipeItem` 三方法原文要点

字段与构造（`RecipeItem.cs:6-23`）：`specific=false`、`specificId`、`isLiquid=false`、`quality`、`minimumCondition = 0.9f`、`destroyItem = true`、`ignoredId`；构造 `RecipeItem(float minimumCondition = 0.9f)` 只赋 `minimumCondition`（配方字面量实际是直接写字段，不走构造）。

**① `GetMatchingItem(List<Item> items, List<Item> exclusions)`（`RecipeItem.cs:25-76`）**


**② `DoesUseItemType(Item item)`（`RecipeItem.cs:78-116`）**：与 ① 同结构，但用 **`HasCommonQuality`（只比 id）**，且液体分支用**未缩放的 `value.qualities`**，忽略 `amount` 与 `condition`，用于「这个物品能不能进某个配方」的 UI 过滤（`Recipes.GetVisibleRecipes(Item filterItem)`，`Recipes.cs:4435-4452`）。

匹配判据汇总：

| 槽位类型 | 匹配条件 | 依据 |
| --- | --- | --- |
| 固体 specific | `item.id == specificId && item.condition >= minimumCondition` | `RecipeItem.cs:64` |
| 固体非 specific | `item.condition >= minimumCondition` **且** 存在同 id 且 `q.amount >= requirement` | `RecipeItem.cs:69`、`Item.cs:225` |

### A.5 实际消耗量的计算（含 `Mathf.Lerp` 行为）

```csharp
// RecipeItem.cs:118-176
public void UseItem(Item item)
{
	if (!item) return;
	if (isLiquid)
	{
		if (!item.TryGetComponent<WaterContainerItem>(out var component)) return;
		if (!specific)
		{
			string id = ""; float max = 0f;
			foreach (LiquidStack item2 in component.stack)
			{
				Liquids.Registry.TryGetValue(item2.liquidId, out var value);
				CraftingQuality qualityThatMeetsCriteria = Item.GetQualityThatMeetsCriteria(quality, value.GetScaledQualities(item2.amount));
				if (qualityThatMeetsCriteria != null)
				{
					id = item2.liquidId;
					max = Mathf.Lerp(0f, item2.amount, quality.amount / qualityThatMeetsCriteria.amount);
					break;                                    // ← 只看第一个满足的 stack
				}
			}
			component.Drain(component.CalculateDrainSingleLiquid(id, max));
		}
		else
		{
			component.Drain(component.CalculateDrainSingleLiquid(specificId, minimumCondition));
		}
		return;
	}
	if ((bool)item.battery && destroyItem) item.battery.UnloadBattery();
	if (specific) item.condition -= minimumCondition;
	else
	{
		CraftingQuality qualityThatMeetsCriteria2 = Item.GetQualityThatMeetsCriteria(quality, item.Stats.qualities);
		float num = quality.amount / qualityThatMeetsCriteria2.amount;
		item.condition -= num;
	}
	if (destroyItem)
	{
		if (item.TryGetComponent<Container>(out var component2)) component2.UnloadAllItems();
		PlayerCamera.main.body.DropItem(item);
		Object.Destroy(item.gameObject);
	}
}
```

**固体槽位（condition 是 0~1 的浮点，`Item.cs:21`）**

- non-specific：消耗**比例** `Δ = quality.amount / q.amount`（`RecipeItem.cs:163-165`）。`q` 是 `item.Stats.qualities` 里第一个 `id` 相同且 `amount ≥ 需求` 的项（`Item.cs:225`），因此 `Δ ∈ (0, 1]`。
  - 例：`hammering 4f` 需求（`Recipes.cs:767`）用 `sledgehammer`（`hammering 1000f`，`Item.cs:4721`）→ 每次只掉 `0.004` condition（约 250 次）。
  - 例：`cutting 1f` 需求用 `flimsyknife`（`cutting 8f`，`Item.cs:6962`）→ 每次掉 `0.125`（8 次用完）。
  - 「剩余可用次数」= `floor(item.condition × q.amount / quality.amount)`（**游戏没有这个字段，需自行计算**）。
- specific：消耗**绝对值** `minimumCondition`（`RecipeItem.cs:159`）。配方里多数 specific 固体槽位写 `minimumCondition = 0f` → **condition 完全不减，物品仅被销毁**（若 `destroyItem`）。相反，若某 specific 槽位没写 `minimumCondition`，则用默认 `0.9f`：要求 `condition ≥ 0.9` 并直接扣掉 0.9。

**液体槽位（单位 mL）**

- non-specific：`max = Mathf.Lerp(0f, stack.amount, quality.amount / q.amount)`。
  - Unity 的 `Mathf.Lerp(a,b,t)` 会把 `t` 夹到 `[0,1]`（等价于 `LerpUnclamped` + `Clamp01`）；此处因为 `q.amount = 密度 × stack.amount ≥ quality.amount`（`Item.cs:225` 已过滤），`t ∈ (0,1]` 恒成立，**clamp 只是安全网、不改变结果**。
  - 代入得 `max = stack.amount × quality.amount / (密度 × stack.amount) = quality.amount / 密度`，即**恰好是满足需求所需的 mL**，与容器里有多少液无关。
  - 然后 `CalculateDrainSingleLiquid(id, max)` 生成 `list[i] = (stack[i].liquidId == id) ? Mathf.Min(stack[i].amount, max) : 0f`（`WaterContainerItem.cs:134-146`），`Drain` 按位相减并 `RemoveAll(s => s.amount < 0.5f)`（`WaterContainerItem.cs:148-159`）——**残液 < 0.5 mL 的 stack 会被直接丢弃**。
  - `break` 在第一个满足条件的 stack 上 → 一个槽位只从**一个** stack 扣液；容器里若有多种液体，优先用 `stack` 列表里靠前的。
  - 容器 `condition` 是液量比例（`WaterContainerItem.cs:227-230`：`item.condition = CurrentTotal / Capacity`），随 `Drain` 自动更新。
- specific：`Drain(CalculateDrainSingleLiquid(specificId, minimumCondition))`（`RecipeItem.cs:149`）→ 精确扣 `minimumCondition` mL。
  - ⚠️ **默认值陷阱**：`morphine` 配方的 `opium` 与 `biochem` 槽位只写了 `specificId` 和 `isLiquid`（`Recipes.cs:281-282`、`286-287`），没写 `minimumCondition` → 用字段默认 `0.9f`，即**每次只耗 0.9 mL**（`opium` 配方里对应槽位显式写了 `minimumCondition = 10f`，`Recipes.cs:258`）。

### A.6 一个槽位只消耗一个物品；`destroyItem` 语义

- 一个 `RecipeItem` 一次只匹配并消耗**一个** `Item`（`GetMatchingItem` 返回单个引用，`UseItem` 只处理它）。
- `destroyItem = true`（默认）→ `PlayerCamera.main.body.DropItem(item); Object.Destroy(item.gameObject);`（`RecipeItem.cs:167-175`）：物品先被丢出（若在容器里）再销毁 GameObject，**整件物品消失**（剩余 condition 一并作废）。若该物品是 `Container` 会先 `UnloadAllItems()`；若带 `battery` 会先 `UnloadBattery()`（`RecipeItem.cs:153-156`）。
- `destroyItem = false`（所有工具槽位：hammering / cutting / nails / heatsource / firestarter 等）→ 物品保留，仅扣 condition，且**不会被加入 `exclusions`**（`Recipe.cs:133-136` 只在 `item.destroyItem && !item.isLiquid` 时排除）→ 同一个实例可被同一配方的**多个槽位**复用（例如一把锤子同时满足两个 hammering 槽位），每槽各扣一次 condition。
- 液体槽位永不进 `exclusions` → 同一个水壶可被多个液体槽位复用（只要每次都能匹配）。

### B.3 id 与「物品 id / 语言包」的关系

1. **性质 id 与物品 id 有 3 处同名，必须分清命名空间**：`foliage`（物品 `Item.cs:3444`）、`nails`（物品 `Item.cs:6733`）、`disinfectant`（物品 `Item.cs:2025`，但它的 liquid 才是消毒性质来源）。同名纯属巧合，`RecipeItem.quality.id` 是查 `qualities` 列表，`specificId` 才是查 `item.id`/液体 id。
2. **有「液体 id == 性质 id」的情况**：`water`、`blood`、`disinfectant`、`fat` 既是 `Liquids.Registry` 的键（`Liquids.cs:15,1430,1510,1644`），也是性质 id。液体 `water` 恰好带 `water 1f` 密度（`Liquids.cs:29`），但 `fat` 液体带的是 `fat 1f`（`Liquids.cs:1661`），`soap` 液体反而带的是 `disinfectant 0.05f`（`Liquids.cs:1687`）——**不能假设「液体 id = 它提供的性质」**。
3. **语言包里有、但配方里没用到的 `cq` 键：没有**。EN.json 与 zh-CN.json 各 18 个 `cq*` 键，与 §B.1 的 18 个 id 完全一一对应（无多余、无缺失）。反之，配方里用到的 18 个 id 也都有语言条目 → 不会出现 `cqxxx` 原样显示。
4. 语言包里另有 `craftanytool / craftanyitem / craftanyliquid / craftliquidquality / craftml / craftitemquality / craftcondition / craftexample / itemqualities / itemvalue / favouriteditem` 等**配方 UI 文案**（`PlayerCamera.cs:639-665`、`1456`、`1466`），模组做 UI 时可直接复用这些键。
5. 其他 3 个中文语言包（联机中文、维基中文 v1.6.5/v1.7.5）中 4 个键的译名与官方 zh-CN 不同（`cqnails`=钉子、`cqproduce`=农产品、`cqflammable`=易燃的、`cqcondiment`=调味料），键本身一致。

### C.2 有没有「工具剩余使用次数」概念？

**没有。** 全树 grep `[Dd]urability` 只命中 `wearableHitDurabilityLossMultiplier`（`ItemInfo.cs:63` 声明；`Item.cs:1187…6532` 的护甲数值；消费点只有 `Limb.cs:374` 与 `GroundGlass.cs:14` 的受击磨损）。没有 `uses`、没有 `remainingUses`、没有工具耐久计数器。工具的「使用次数」只能用 `item.condition` 与性质点数**现算**：

- 固体非 specific：`剩余次数 = condition / (quality.amount / q.amount)`（向下取整要自己算，且每次扣除会让 condition 逼近 0）。
- 固体 specific：`minimumCondition` 为 0 时**永不磨损**（只受 `destroyItem` 影响）；否则 `次数 = condition / minimumCondition`。
- 电池类物品另有 `BatteryItem` 电量（`RecipeItem.cs:153-156` 里 `item.battery.UnloadBattery()`），但那是电力、不是合成耐久。
- `ItemInfo.destroyAtZeroCondition`（`ItemInfo.cs:39`）会让 condition 归零的物体在 `Item.Update` 里被销毁 → 模组不能假设「工具永远存在」。

### C.3 `Item.favourited` 在合成选材里的作用

- 声明：`Item.cs:23-24`（`[HideInInspector]` + `public bool favourited;`，默认 `false`）。
- **合成选材：被硬跳过**——`RecipeItem.GetMatchingItem` 第一句就是 `if (item.favourited || (item.id == ignoredId && !isLiquid) || exclusions.Contains(item)) continue;`（`RecipeItem.cs:29`）→ **原版永远不会用收藏物品做材料**（固体与液体都跳过）。模组若自己做选择，必须保持同样语义，否则会出现「原版能造、模组说缺料」或反之的不一致。
- **这正是原版设计意图**：教学关卡要求玩家把 `flimsyknife` **设为收藏**后才继续（`CraftingCourse.cs:197-207`：`if (allItem.id == "flimsyknife" && allItem.favourited) return true;`），即「收藏 = 保护这件工具不被合成吃掉」。
- 切换入口（玩家按键）：`PlayerCamera.cs:1880`：`component2.GetItem().favourited = !component2.GetItem().favourited;`
- 其他相关点：`Item.fullName` 加收藏图标（`Item.cs:62` 的 `<sprite index=22>`）、物品栏角标 `InvButton.cs:165`、提示文案 `PlayerCamera.cs:1477-1480`（`Locale.GetOther("favouriteditem")`）、存档持久化 `SaveSystem.cs:56,85,109,139,298`、换电池时保留收藏位 `BatteryPreset.cs:96,111`（同 `BatteryItem.cs:96,111`）。

## D. 给写模组的人的结论（可拿到 / 拿不到 / 坑）

1. **能拿到（全部 public）**：`item.Stats.qualities`（永不为 null）、`item.condition`、`ItemInfo.value` / `GetValue(item)` / `weight` / `totalWeight` / `tags`/`GetTags()`/`HasTag()`、`item.favourited`、`Liquids.Registry[liquidId].qualities` + `GetScaledQualities(ml)`、`RecipeItem.{quality,minimumCondition,specific,specificId,isLiquid,destroyItem,ignoredId}`、`Recipe.{items,result,INT,index,category}`、`RecipeResult.{id,isLiquid,amount,resultCondition}`。候选材料池用 `Body.GetAllItemsThorough()`（`Body.cs:871`）+ `Recipe.GetItemsForRecipeThorough()`（`Recipe.cs:144-174`，UISafe，缺料位置为 `null`）。
2. **拿不到**：没有耐久/剩余次数计数器（§C.2），没有「物品单价」之外的收益概念，也没有任何按性质排序的现有代码——排序逻辑要自己写；「贵不贵」只能从 `GetValue(item)`、`value`、`weight`、`tags` 组合出自定义权重（`GetValue` 已自动乘 `condition`，天然把「用旧的工具」算便宜）。
3. **排序公式**（建议直接抄）：设槽位需求为 `req`，候选物品该项性质点数为 `q` → 固体单次成本 `Δ = req.amount / q`；若按「价值损失」排序则 `cost = GetValue(item) × Δ`（越小越省），若按「耐久余量」排序则 `uses = condition / Δ`（越大越耐用）。液体单次成本 `mL = req.amount / 密度`，按 `valuePerLiter` 相乘可得液体价值损失（`ItemInfo.GetValue` 用的是同一系数：`amount × 0.001 × valuePerLiter`，`ItemInfo.cs:115`）。
4. **`Mathf.Lerp` 的坑**：液体消耗走 `Mathf.Lerp(0f, stack.amount, req/actual)`（`RecipeItem.cs:141`），Unity 会把第三参夹到 `[0,1]`；在本代码路径里 `req/actual ≤ 1` 恒成立（匹配阶段已过滤 `q.amount >= req`），所以结果 = `req / 密度`。**但如果你自己复制这段逻辑用于「部分扣液」，务必记得 clamp 会让超大需求只扣满整瓶。**
5. **必须复刻的「不可选」规则**（否则模组的预判与原版不一致）：`favourited` 跳过（`RecipeItem.cs:29`）、`item.id == ignoredId`（= 配方产物 id，`Recipes.cs:4430`）的固体跳过、已在 `exclusions` 里的实例跳过、**非空 `Container` 跳过**（`RecipeItem.cs:58-61`）、`condition < minimumCondition` 跳过。容器那条最容易踩：有东西的背包永远不能当材料，而**只有液体的容器 `itemCount == 0`，可以用**。
6. **`minimumCondition` 默认值是 0.9，不是 0**（`RecipeItem.cs:14`）：固体非 specific 槽位普遍显式写 `minimumCondition = 0f`，但**液体 specific 槽位经常不写**（morphine 的 opium/biochem 槽位，`Recipes.cs:281-287`）→ 真实需求是 0.9 mL。判断「这个槽位要多少」必须读字段值，不能按 0 猜。
7. **`specific` 是派生字段**：不要靠读 `specificId != null` 之外的方式判断（空字符串也要当 false）。`Recipes.SetUpRecipes()` 在末尾统一 `specific = !string.IsNullOrEmpty(specificId)` 并写 `ignoredId`（`Recipes.cs:4421-4432`）。模组新增配方时若在 Postfix 里追加，**必须自己设 `Recipe.index`**（原版赋值发生在该方法体内部，Postfix 之后才追加的配方拿不到 index）。
8. **`Liquids.Registry` 缺键会 NRE，不是静默失败**：`RecipeItem.cs:49-50`（以及 `:136-137`）用的是 `TryGetValue(..., out var value)` 却**没有判空**，紧接着 `value.GetScaledQualities(...)` → 只要容器里存在一个未注册的 `liquidId`（存档损坏、其他模组注入的液体、被删除的液体），匹配阶段就抛 `NullReferenceException`。模组的扫描/排序逻辑**必须自己判空并 `continue`**，最好把这种 stack 记为「不可用」而不是崩溃。`Liquids.cs:15` 的键写法是 `["<liquidId>"] = new LiquidType`，可直接 `Registry.ContainsKey` 校验。
9. **性质 id 大小写与显示名**：id 全小写、无分隔符（如 `heatsource`、`firestarter`）。显示名请统一走 `quality.LocaleName`（= `Locale.GetOther("cq"+id)`，`CraftingQuality.cs:7`），它会自动跟随语言；缺键时返回 `cq<id>`（`Locale.cs:103-108`）而不是报错——**模组自定义性质 id 若想有中文名，必须自己注入 Locale 字典或接受原始键显示**。原版显示格式是 `名称 (点数)`，用 `quality.amount.ToString("0.#")`（`PlayerCamera.cs:1460`）。
10. **运行时注入点与顺序**：`Item.SetupItems()`（`Item.cs:233`，调用点 `WorldGeneration.cs:258`）先于 `Recipes.SetUpRecipes()`（`Recipes.cs:38`，调用点 `WorldGeneration.cs:259`）执行。模组若要新增 `ItemInfo`，**必须在 `SetupItems` 之后自行调用 `SetTags()`**（否则 `GetTags()` 返回 null、`HasTag()` NRE，连 `Item.Start`（`Item.cs:96-103` 的 `Stats.HasTag("cangetwet")`）都会炸）；新增配方则 Harmony Postfix 到 `Recipes.SetUpRecipes` 并自行设 `Recipe.index` 与 `RecipeItem.specific`/`ignoredId`。`Item.GetItem(id)` 内部是 `GlobalItems[id]`（`Item.cs:6978-6981`），**未知 id 直接抛 `KeyNotFoundException`**，模组查询一律用 `Item.GlobalItems.TryGetValue`。
11. **`ItemInfo` 是全局单例**（`Item.cs:17` 的 `GlobalItems`，`Item.Stats => GetItem(id)`，`Item.cs:64`）：改 `qualities` 会影响该类**所有**实例；「按实例自定义性价比」只能放在模组自己的缓存里（以 `Item` 实例或 `GetInstanceID()` 为键）。
12. **液体性质与容器**：容器 `condition` = 液量/容量（`WaterContainerItem.cs:227-230`），所以「液体槽位」不消耗 condition、也不会销毁容器；`Drain` 会**丢弃残液 < 0.5 mL 的 stack**（`WaterContainerItem.cs:156`）——模组若在 UI 里预告「扣完还剩多少」，小于 0.5 mL 时应显示为 0（会被清掉）。
13. **`ignoredId` 只对固体生效**（`RecipeItem.cs:29` 的 `&& !isLiquid`），液体槽位即使 `liquidId == 产物 id` 也允许（例如用 `blood` 液体造 `blood`）。模组复刻规则时别一刀切。
14. **性能**：`Recipe.GetItemsForRecipeThorough()` 每次都会 `Physics2D.OverlapCircleAll(pos, 10f, LayerMask.GetMask("Item"))`（`Recipe.cs:119,149`）——半径 10、每帧调用会很贵。模组做「一键最优选材」时应自己缓存一次物品列表（同一帧内复用），不要对每个配方都重算。
