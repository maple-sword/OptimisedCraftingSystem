# 流体（液体）存放逻辑重做方案

> 对象：BetterInventoryLogic 1.0.5（`CraftingLogic.dll`，命名空间 `BalaurBohemianBroken`）的液体存放链路。
> 目标：给出 ≥4 个**取舍哲学互不相同**的可选方案，供 OptimisedCraftingSystem 立项时选择。
> 约束：本文**只做设计与分析，不含任何实现代码**；所有游戏 API 均取自本机反编译树 `D:\maple_sword\workspace\_GameSource\Assembly-CSharp\`（下称 `_GameSource`），已逐条 read/grep 核对。
> 行号说明：`_GameSource\Assembly-CSharp\` 中同一类型被反编译拆进多个同名副本（如 `Body.cs` / `LimbNum.cs` / `SleepQuality.cs` / `WorkoutType.cs` 内容相同），行号跨副本一致；本文统一引用**与类型同名**的文件。不确定的结论一律显式标注「未确认」。

## 0. 现状取证（改之前必须承认的事实）

### 0.1 现有实现的三处结构性选择

| 现象 | 证据 | 性质 |
|---|---|---|
| 只挑「一次装得下」的瓶子 | `LiquidStorageLogic.cs:92` `if (liquid_container.SpaceLeft < liquid_amount) continue;` | **纯策略选择**，不是 API 限制 |
| 候选池只有「身上」 | `LiquidStorageLogic.cs:88` 只遍历 `PlayerCamera.main.body.GetAllItemsThorough()` | 策略选择 |
| 存放结果按瓶名去重 | `LiquidStorageLogic.cs:119-132` 往 `StorageLogic.storing_in`（`HashSet<string>`）塞「瓶子名 (容器名)」 | 数据结构限制 |
| 整体替换 `SpawnResult` | `Patches.cs:93-96` Prefix + `Patches.cs:168` 无条件 `return false` | **架构债**（`Patches.cs:98-105` 作者自述：transpiler 更耐用，但 Prefix 开发快） |
| 临时瓶 5 分钟后连液体一起消失 | `Patches.cs:138-146`，`:143` 先 `StorageLogic.AutoPickup` 入包，`:145` 再 `Object.Destroy(gameObject, 300f)` | 继承自原版 `RecipeResult.cs:59-64`，但**入包后仍被销毁** |

### 0.2 三个「反直觉」的游戏事实（方案的硬约束）

1. **`AddLiquid` 本身就支持部分填充，并返回实装量。**
   `WaterContainerItem.cs:98-116`：`float num = Mathf.Min(SpaceLeft, amount);`（`:100`）→ 同名 stack 累加，否则 `stack.Add(new LiquidStack(...))`（`:112`）→ `UpdateCondition()`（`:114`）→ `return num;`（`:115`）。
   ⇒ 现有 `SpaceLeft < amount → continue` 是**自己放弃**了这个能力。
2. **液体容器的 `condition` 就是填充率，不是耐久。**
   `WaterContainerItem.cs:227` `UpdateCondition() { item.condition = CurrentTotal / Capacity; }`；而 `Item.cs:86-94 SetCondition(float)` 在物品含 `WaterContainerItem` 时**会按比例真的倒掉液体**（`:91` `component.Drain(component.CalculateDrain(component.Capacity * (1f - num)))`）。
   ⇒ **绝不能用 `SetCondition` 去"修"一个装了液体的瓶子**。
3. **`Drain` 会静默吞掉小于 0.5 的余量。**
   `WaterContainerItem.cs:148-159`：要求 `toRemove.Count == stack.Count`（`:150`），末尾 `stack.RemoveAll(s => s.amount < 0.5f)`（`:156`）。
   ⇒ 分装/搬运的余额计算必须用 `AddLiquid` 的**返回值**做闭环，不要用 `CalculateDrain` 的近似值。

## 方案 A：余量续瓶（Split Pour / 多瓶分摊）

**① 一句话目标**：一次合成的液体应尽力装进**已有的**瓶子，余量依次流向下一个瓶子；只有所有瓶子都满了才允许造临时瓶。

**② 决策流程**

```
输入: liquid_id, amount, body = PlayerCamera.main.body
candidates ← body.GetAllItemsThorough()                                   // Body.cs:871
             .Where(i => i.TryGetComponent<WaterContainerItem>(out w)
                         && w.SpaceLeft > 0f)                             // WaterContainerItem.cs:51
             .Where(过 can_fill_new_bottles / can_stack_into_mixed 闸门)   // 沿用 LiquidStorageLogic.cs:94-107
排序: SpaceLeft 降序 → 同余量时沿用原比较器栈(重量比/纯度)               // LiquidStorageLogic.cs:66-84
remaining ← amount; used ← []
for w in candidates:
    if remaining < min_fill_ml: break                                      // 避免制造 3mL 渣瓶
    added ← w.AddLiquid(liquid_id, remaining)                              // WaterContainerItem.cs:98, 返回实装量
    if added <= 0f: continue
    remaining ← remaining - added
    used.Add(w);  staging.Add(名字(w))                                     // 通知用
    if remaining <= 0.5f: remaining ← 0f; break                            // 对齐 Drain 的 0.5 阈值(:156)
if remaining > 0f && create_temp_bottle:
    GameObject g ← Utils.Create("craftingbottle", body.transform.position, 0f)  // Utils.cs:8
    w2 ← g.GetComponent<WaterContainerItem>(); w2.AddLiquid(liquid_id, remaining)
    w2.GetComponent<Item>().condition ← remaining / w2.Capacity             // 直接赋值, 不用 SetCondition
    StorageLogic.AutoPickup(item, body); 挂接生命周期(见方案 D)
通知: Body 侧把 used 里每个瓶名加入本批结果集合(改成 List, 不用 HashSet 去重)
```

**③ 新增设置项**

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `liquids_allow_split_pour` | `SettingBool` | `true` | 总开关；关掉即退回现有行为 |
| `liquids_split_min_fill` | `SettingFloat`（0–500） | `50` | 单个瓶子至少装这么多才值得占用 |
| `liquids_split_max_bottles` | `SettingInt`（1–8） | `3` | 防止把 30 个瓶子都沾一遍 |
| `liquids_split_then_temp` | `SettingBool` | `true` | 分摊后仍有余量时是否再造临时瓶 |

**④ 兼容性与风险**
- 与原版 `RecipeResult.cs:50` 语义分叉：原版要求「单一液体 + 全装得下」，本方案会出现"一次合成写进 3 个瓶子"。**只影响合成路径**，玩家手动倒液仍走 `Body.CombineLiquids`（`Body.cs:1533`），不会互相干扰。
- 与 **CUCoreLib** 的 `SpawnResult` Prefix（`RecipeRegistryPatches.cs:101`）**不冲突**：它 `:105` 在 `__instance.isLiquid` 时直接 `return true` 放行，但 CraftingLogic 的 `return false`（`Patches.cs:168`）会让它根本不执行——需要留意的是**反向**问题（见 ⑤ 与总表）。
- 与 **汉化模组**：新增提示文案必须走 `Locale.LoadLanguage` Postfix（现有用法 `Patches.cs:28`），且**不要**提高 priority（汉化用 200 在其后按索引器覆盖，见 `_analysis\BetterInventoryLogic-改进与新增功能分析.md` 第 4 节）。
- 存档：**零新增持久化**。分摊只改变"这一批液体落在哪几个 `stack` 里"，而 `stack` 本来就随 `WaterContainerItem` 存档（`WaterContainerItem.cs:11`，`SaveSystem.cs:62-87`）。
- 风险点：`StorageLogic.storing_in` 是 `HashSet<string>`（`StorageLogic.cs`），多瓶同名会被去重成一条 → 提示会**少报**；必须同步改成有序列表，否则玩家看到"存进了 1 个瓶子"却是 3 个。

**⑤ 工作量**：**小**（改动局限在 `FindBestBottle` / `StoreLiquid` 两个方法内，约 60–100 行）。
**不可逆设计代价**：一旦玩家习惯"余量自动续瓶"，就再也不能回到"一次装不下就造临时瓶"（那会被视为丢液体）；且**通知的数据模型**（一个结果 → 多个落点）一旦定下，后续所有面向玩家的文案/日志格式都被它绑定。

**⑥ 玩家可感知**
- 优点：不再因为"就差 20mL"而凭空多出一个临时瓶；背包里 3 个半瓶水会被自动填满，直接减少物品数量与整理负担。
- 缺点：液体会"散"到多个瓶子里，玩家想找"我的 300mL 水在哪"变难；若与方案 C 的纯度策略叠加，可能把纯水兑进混液瓶（需靠闸门控制）。

## 方案 B：显式目标指定（收藏即指令 / 溢出链）

**① 一句话目标**：玩家可以用**完全不新增 UI** 的方式指定"这批液体倒进哪个容器"，模组只在该容器装不下时才溢出到别处。

**② 决策流程**

```
designated ← body.GetAllItemsThorough()                                   // Body.cs:871
             .Where(i => i.TryGetComponent<WaterContainerItem>(out w)
                         && i.favourited)                                 // Item.cs:24, 玩家用 favourite 键切换
             .Where(该瓶可接收 liquid_id)                                  // 纯度闸门, 见方案 C
if designated 非空:
    target ← 其中 SpaceLeft 最大者                                          // WaterContainerItem.cs:51
    added ← target.AddLiquid(liquid_id, amount)                            // :98
    remaining ← amount - added
    if target 所在容器已超重(Container.AboveHoldingWeight, Container.cs:90):
        DoAlert(容器超重提示)                                              // PlayerCamera.cs:2810
else:
    remaining ← amount                                                     // 回落方案 A
if remaining > 0f:
    按 overflow_policy 处理: ① 方案 A 分摊  ② 造临时瓶  ③ 不装, 弹出原版倒液 UI
    // ③ 用 PlayerCamera.main.StartLiquidTransfer(target, 临时瓶成分) 复用原版 UI, 见 PlayerCamera.cs:1669
可发现性: 在 ItemHoverDescription 里为"指定容器"追加一行标记                     // PlayerCamera.cs:1304 出口; 原版已为 favourited 加提示 :1477-1479
```

**为什么可以复用 `favourited`**：`Item.cs:24 public bool favourited;`，由 `PlayerCamera.cs:1878-1882`（`Input.GetKeyDown(KeyBinds.GetBind("favourite"))` 悬停背包格）切换，`Item.cs:62` 的 `fullName` 里已经会显示 `<sprite index=22>` 图标，`PlayerCamera.cs:1477-1479` 已经会追加一段说明文字，并且**它随存档保存**（`SaveSystem.cs:56 / :298`、`SavedItem.cs:11`）。零新 UI、零新存档。

**③ 新增设置项**

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `liquids_honor_favourite` | `SettingBool` | `true` | 是否把收藏的液体容器当作指定目标 |
| `liquids_favourite_overflow` | `SettingDropdown`〔分摊/临时瓶/不装并开原版倒液 UI〕 | 索引 0（分摊） | 溢出策略 |
| `liquids_favourite_hint` | `SettingBool` | `true` | 是否在悬浮说明里标注"已设为液体目标" |

**④ 兼容性与风险**
- **语义污染是本方案最大的问题**：原版 `favourited` 的既定含义是"防误耗"——`RecipeItem.cs:29` 明确把收藏物品排除出配方材料。把它同时当作"液体目标位"，会让"我不想让这个水壶被合成吃掉"与"我要往这个水壶里倒水"共用一个开关。本模组已整体接管选材（`CraftingLogic.cs:134 GetItemsForRecipe`），其中是否保留 favourited 排除**未确认**，必须实测；若不保留，玩家会感到"收藏在这个模组里不防误耗、却影响倒水"。
- 与其他模组：`CUQuickPickup` / `CuHotbar` / `QoL Unknown` 与物品格交互有关但无方法级重叠（`Body.DoPickupCheck` / `FirstEmptySlot` / `PickUpItem` 一线）；真正的重叠方是**任何也把 `favourited` 当语义位的模组**（本机清单里未发现，但 CUCoreLib 自定义物品体系存在）。
- 存档：`favourited` 已持久化，**旧存档天然兼容**；反过来，玩家一旦养成"收藏=液体目标"的习惯，卸载本模组后这些收藏会退回成单纯的"防误耗"标记（无害但不直观）。
- 嵌套容器：不存在（`Container.cs:116-123` 禁止嵌套），所以"倒进背包里的水壶"= 两层，`GetAllItemsThorough()`（`Body.cs:871`）已经能拿到，**不需要**自定义递归遍历。

**⑤ 工作量**：**中**（`favourited` 复用是小活，但"溢出策略 + 悬浮说明注入 + 与收藏语义的冲突处理"要各写一段；约 150–200 行，且需要实测原版倒液 UI 的复用）。
**不可逆设计代价**：把玩家可见的**既有字段**征用为存储指令位。一旦发布，玩家存档里就分不清"这些收藏是防误耗还是液体目标"；想改成专用标记就必须做**存档语义迁移**，且迁移无法区分玩家意图。

**⑥ 玩家可感知**
- 优点：这是最符合直觉的一条——"我把这个水壶收藏了，合成的药水就该进这个壶"；零学习成本以外的 UI 成本，且能跨存档记住。
- 缺点：一个开关两种含义，玩家会困惑；如果收藏了多个瓶子，行为取决于排序规则（需在提示里说明选中了谁）。

## 方案 C：纯度台账（Liquid Ledger / 允许-禁止混合的策略层）

**① 一句话目标**：把"能不能混"从"看瓶子里有什么"升级为**台账不变量**：每种液体有明确的可混/禁混与品质衰减规则，危险液体永不混入任何瓶子。

**② 决策流程**

```
规则来源(优先级从低到高):
  ① 内置: 纯净水/血/血清 等"高价值液体"默认独立; Liquids.DangerList 全部隔离   // Liquids.cs:7 (mindwipe, bleach, fentanyl, ... 12 项)
  ② 品类: 定义"同族可混"表(如所有 juice 同族); 液体元数据取 LiquidType            // LiquidType.cs (:localeName/:valuePerLiter/:qualities)
  ③ 玩家 JSON 覆盖(见方案 E)

判定一个候选瓶 w 能否接收 liquid_id:
  if !Liquids.Registry.TryGetValue(liquid_id, out t): 按"未知液体"从严处理   // Liquids.cs:13, 别用索引器
  if w.CurrentTotal <= 0f: 允许(空瓶)                                       // :49
  if w.HasLiquid(liquid_id): 允许(补同一液体)                               // :53
  switch purity_mode:
     严格禁止混合 → 拒绝
     纯净优先     → 拒绝, 但记入"降级候选"列表
     允许混合     → 检查 danger 规则: 若 w 含 DangerList 液体 或 liquid_id ∈ DangerList → 拒绝

写入时的品质处理:
  added ← w.AddLiquid(liquid_id, amount)                                     // WaterContainerItem.cs:98
  混合液体不改变 stack 数值, 只在"价值/效果"层面衰减:
     评估用 LiquidType.GetScaledQualities(ml) 的加权平均                        // LiquidType.cs:30
     若 purity_mode == 纯净优先 且发生了混合: 把结果 value 按 mixing_quality_decay 打折
     注意: 这只是"模组口径"的品质提示, 不改原版数值(见风险)

存档: 台账写入自建 [Saveable] 组件(public 字段)                              // Saveable.cs:1-6, 读回 SaveSystem.cs:348-358
      若装了 CUCoreLib 则改注册 SaveRegistry.RegisterItemProvider               // SaveRegistry.cs:47, IItemSaveProvider.cs:7-11
```

**③ 新增设置项**

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `liquids_purity_mode` | `SettingDropdown`〔允许混合/纯净优先/严格禁止〕 | 索引 1（纯净优先） | 策略档位 |
| `liquids_mix_decay` | `SettingFloat`（0–1） | `0.5` | 混合后的品质折算系数（仅提示层面） |
| `liquids_isolate_danger` | `SettingBool` | `true` | `Liquids.DangerList` 液体强制独占瓶 |
| `liquids_ledger_persist` | `SettingBool` | `true` | 是否把台账写进存档 |

**④ 兼容性与风险**
- **"台账"不是原版概念**，`WaterContainerItem.stack`（`:11`）里只有 `liquidId` 与 `amount`（`LiquidStack.cs`），没有品质字段。因此台账只能：**(a) 作为排序/选择依据**（安全，无存档负担），或 **(b) 附带一个品质乘数随瓶保存**（有存档负担，且必须回答"原版 `Drink`/`ApplyToLimb`/`Inject` 不会读这个乘数"——即**玩家喝下去的效果不会真的变差**，见 `WaterContainerItem.cs:167 / :185 / :202`）。方案的价值主张必须诚实地限定在 (a) 或说明 (b) 是"只影响显示与后续合成取值"。
- 与 **CUCoreLib** 自定义液体：`LiquidRegistry.GetRegisteredLiquidIds()`（`LiquidRegistry.cs:117`）会在运行时加入新 id。台账规则必须能容忍**未知 id**，且读取 `Liquids.Registry` 一律用 `TryGetValue`（现有模组在 `CraftingLogic.cs:297 / :305` 用的是索引器，会 `KeyNotFoundException`——这是**现存的 P0 级缺陷**，见 `_analysis\BetterInventoryLogic-改进与新增功能分析.md` 2.1 节）。
- 与 **CUCoreLib** 的 `WaterContainerItem.Start` Postfix（`ItemRegistryPatches.cs:91`，给自定义液体上掩码）无冲突，但两者都会改写 `stack` 的初值，顺序敏感（未确认）。
- 存档：**(a) 形态零存档改动**；**(b) 形态是新的存档契约**——`[Saveable]` 组件的 public 字段一旦发布，字段名/类型就是硬契约（`SaveSystem.cs:348` 只找 public 字段，`:334` 找不到类型只弹 Alert 不崩溃）。若走 CUCoreLib 的 `IItemSaveProvider`（`SaveRegistry.cs:47`），则变成**跨模组契约**：CUCoreLib 的 `GetVersion()`（`IItemSaveProvider.cs:7`）就是为版本迁移准备的，比裸 `[Saveable]` 正规。
- 风险：**卸载模组后的孤儿数据**——存档里残留的台账组件不影响加载（`SaveSystem.cs:335-339` 只提示），但如果用 (b) 形态且玩家换了模组版本，品质乘数可能读到旧值而不自知。

**⑤ 工作量**：**中偏大**（规则内核 + 排序接入 + 存档 + 与方案 E 共用的规则解析；约 250–400 行，且要处理未知液体与混合衰减的口径）。
**不可逆设计代价**：**品质衰减公式与"什么算同族"一旦发布就冻结**。改了会让同一份老存档里的液体品质突然跳变；反过来若不冻结，玩家无法建立任何稳定预期。这是"发布即定契约"的典型。

**⑥ 玩家可感知**
- 优点：终于能回答"我这瓶水能不能兑"；危险液体（`Liquids.cs:7` 那 12 种）不会莫名其妙污染你的血袋；排序会主动把液体送进"最合适"的瓶子而不是"第一个装得下"的瓶子。
- 缺点：概念成本最高，玩家需要理解"纯净优先/严格禁止"的区别；如果做成 (b) 形态，会出现"提示说品质 60%，但喝下去效果没变"的割裂感。

## 方案 D：临时瓶生命周期（Temp Bottle Lifecycle）

**① 一句话目标**：临时瓶（`craftingbottle`）是**逃生舱而不是储物柜**——要么尽快把液体并入长期容器，要么明确地让它永久存在，绝不出现"5 分钟后连液体一起消失"。

**② 决策流程**

```
合成结束(液体分支)后:
  temp ← 本批创建的临时瓶(若有)
  if temp == null: return
  if migrate_enabled && temp 内有液体 id:
      // 依次尝试并入长期容器(方案 A 的候选池, 但排除 temp 本身)
      for w in candidates(排除 temp):
          moved ← w.AddLiquid(id, temp.AmountOf(id))                        // WaterContainerItem.cs:82 / :98
          if moved > 0f:
              temp.Drain(temp.CalculateDrainSingleLiquid(id, moved))        // :134 / :148 ; 只丢 <0.5 残渣
          if temp.AmountOf(id) < 0.5f: break
      if temp.CurrentTotal <= 0f:
          交给游戏自清理(以下为原版行为, 无需自己做)
          // CustomItemBehaviour.cs:261-267: craftingbottle 且 CurrentTotal == 0 → Object.Destroy(gameObject)
          撤销原版 300s 定时销毁(若已挂 Object.Destroy(gameObject, 300f))
  根据 temp_bottle_policy 决定寿命:
      原版 5 分钟        → 不干预(保留 Patches.cs:145 的 Object.Destroy(gameObject, 300f))
      空瓶即销毁        → 不挂定时器, 依赖 CustomItemBehaviour.cs:261-267 自我销毁
      永不销毁          → 不挂定时器
  UX: DoAlert 说明"临时瓶：<液体名> <量>mL，建议尽快倒入容器"                     // PlayerCamera.cs:2810
```

**③ 新增设置项**

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `liquids_temp_policy` | `SettingDropdown`〔原版 5 分钟 / 空瓶即销毁 / 永不销毁〕 | 索引 2（永不销毁） | 生命周期 |
| `liquids_temp_auto_migrate` | `SettingBool` | `true` | 造出来后**立刻**尝试并入长期容器 |
| `liquids_temp_migrate_on_drink` | `SettingBool` | `false` | 玩家喝水/注射前是否先做一次归并（未确认是否有干净钩子） |
| `liquids_temp_warn` | `SettingBool` | `true` | 是否提示临时瓶状态 |

**④ 兼容性与风险**
- **这是唯一一条会改动原版行为的方案**：`RecipeResult.cs:59-64` 原版也造 `craftingbottle` 并 `Object.Destroy(gameObject, 300f)`。把 5 分钟改成"永不销毁"意味着**玩家可以无限积累 1000mL 容量的免费瓶子**（`Item.cs:6598-6615`：`craftingbottle` 容量 1000、`category = "unobtainable"`、`weight = 1f`、`value = 0`）→ 直接影响经济与负重平衡。这是**必须让玩家显式选择**的开关，默认值需要你拍板（我倾向默认"永不销毁"，因为丢液体对玩家是纯粹的挫折）。
- 原版**禁止**把液体倒进 `craftingbottle`：`Body.cs:1570-1576` 里 `it1.id != "craftingbottle"` 才 `StartLiquidTransfer`。所以"临时瓶 → 长期容器"**不能用原版倒液 UI 完成**（目标是 craftingbottle 时被拒；来源是 craftingbottle 时未确认是否也被拒——`:1570-1576` 只检查了目标 `it1`，因此手动把临时瓶倒出去**可能可行**，需实测）。这决定了自动归并必须自己做（用 `AddLiquid` + `Drain`），不能只弹 UI 让玩家手动解决。
- 与 **CUCoreLib**：`Utils.Create` 被它补丁（`UtilsCreatePatches.cs:29-43`，`:35` 先试 `Resources.Load`，`:39` 再查注册表，`:43` 走 `CustomInstantiate.InstantiateReturn`），所以 `Utils.Create("craftingbottle", ...)` 仍然命中原版资源，不冲突。
- 与 **`No Self-Destruct on Quit.dll`**：本机装了该插件，名字提示它处理"退出时自毁"，与临时瓶的定时销毁**可能**属于同一类问题域（未确认，需实测两者是否互相影响）。
- 存档：临时瓶在**背包里**时会被存档（`SaveSystem.cs:32-88` 保存 `body.slots` 与其容器子物品），但 `Object.Destroy` 的定时器**不会**被存档保存——重载后定时器消失，瓶子和液体留下。也就是说"5 分钟销毁"**只在同一次会话内生效**，跨存档重载就变成了永久瓶子。这是原版行为的一个不一致，方案 D 可以顺手把它变成明确的一致语义。
- 若走"永不销毁"，**不建议**再加 `[Saveable]` 记录瓶子寿命：那会把一个纯运行时的行为变成存档契约，收益极低。

**⑤ 工作量**：**小**（临时瓶分支就在 `Patches.cs:138-146` 一处，归并逻辑可复用方案 A 的候选池；约 80–150 行）。**若走 CUCoreLib `IItemSaveProvider` 则升为中**。
**不可逆设计代价**：一旦取消定时销毁，玩家会积累大量临时瓶，**只能靠加回收策略收敛，不能再回到"时间到了就消失"**（玩家已经把液体存在里面了）。等于把"临时瓶是消耗品"这一原版设计永久改掉；同时若同时提供"永不销毁"与"归并"，两者的交互语义（归并失败时留不留）也会被玩家当成承诺。

**⑥ 玩家可感知**
- 优点：直接消灭最令人愤怒的失败模式——挂了 4 分钟机回来发现刚合成的药水没了；临时瓶仍然是"用完即弃"的（装空了游戏自己会销毁，`CustomItemBehaviour.cs:261-267`）。
- 缺点：免费 1000mL 容器削弱了"找水壶"这件事；如果归并太激进，玩家会看到液体"自己跑进别的瓶子"，需要靠 `DoAlert` 解释。

## 方案 E：声明式规则表（数据驱动 / 玩家可编程策略）

**① 一句话目标**：把"哪种液体优先存进哪种容器"从代码里搬出来，交给玩家用一份可编辑的规则表定义；模组只当解释器。

**② 决策流程**

```
启动/重载时: 读 rules.json → 编译成有序规则列表(先匹配先赢)
  {
    "version": 1,
    "rules": [
      { "liquid": "water",  "targetItemId": "canteen", "order": "space_desc" },
      { "liquid": "blood",  "targetItemId": "bloodbag", "requireEmpty": true },
      { "liquid": "*",      "targetItemId": "*", "forbidMix": true }        // 兜底
    ]
  }

每次存液(进入 SpawnResult 的液体分支):
  rule ← rules.FirstOrDefault(r => 匹配(r.liquid, liquid_id))
  候选池 ← body.GetAllItemsThorough()                                        // Body.cs:871
           .Where(i => i.id == rule.targetItemId || rule.targetItemId == "*")
           .Where(i => i.TryGetComponent<WaterContainerItem>(out w) && w.SpaceLeft > 0f)
  若 rule.requireEmpty: 只保留 w.CurrentTotal <= 0f                          // WaterContainerItem.cs:49
  若 rule.forbidMix:    只保留 w.CurrentTotal <= 0f || w.HasLiquid(liquid_id) // :53
  排序: rule.order ∈ {space_desc, space_asc, weight_ratio, near_first}
  装填: 复用方案 A 的分摊循环(AddLiquid 返回值闭环)                            // :98
  无匹配候选 → 交给兜底链(方案 D 的临时瓶 / 方案 A 的分摊)

对未在表中出现的液体: 走 builtin 默认表(纯水→水壶, 危险液体→独占)
```

**③ 新增设置项**

> **重要限制（已核验，双重锁死）**：① 原版 `Setting` 只有五个具体子类——`SettingBool`（`SettingBool.cs:1`）、`SettingInt`（`SettingInt.cs:1`）、`SettingFloat`（`SettingFloat.cs:3`）、`SettingDropdown`（`SettingDropdown.cs:1`）、`SettingKeybind`（`SettingKeybind.cs:3`），**没有文本输入项**（`SettingSaveData.cs:4` 是 `Settings.SaveSettings()` 用的序列化 DTO（`Settings.cs:660-673`），**不是** `Setting` 子类，别拿它当控件）。② `Setting` 虽然是 `public abstract`（`Setting.cs:3`），**但自定义子类存不住值**：`Settings.LoadSettings()` 的还原分支只写死了这五种类型（`Settings.cs:621-640`），其它类型被**静默跳过**，值永远回到默认。⇒ 规则表**必须落文件**，不能做成设置项；能用设置项表达的只有布尔/整数/枚举下拉/键位。

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `liquids_rules_enabled` | `SettingBool` | `true` | 是否启用规则表 |
| `liquids_rules_path` | 无（固定路径） | `BepInEx/config/OptimisedCraftingSystem/liquid_rules.json` | 首次运行写出默认规则 |
| `liquids_rules_reload` | `SettingKeybind` | 未绑定（`KeyCode.None`） | 热重载（`SettingKeybind.Apply()` → `KeyBinds.CacheBind`，`SettingKeybind.cs:28`） |
| `liquids_rules_verbose` | `SettingBool` | `false` | 命中哪条规则打日志 |

**④ 兼容性与风险**
- 规则表里的 `liquid` / `targetItemId` 是**原始 id 字符串**，而 CUCoreLib 会在运行时注入自定义液体（`LiquidRegistry.cs:117`）与自定义物品 → **规则必须能容忍未知 id**并给出可读的校验警告，否则玩家改错一个字母就静默失效。建议启动时对 `Liquids.Registry`（`Liquids.cs:13`）与 `Item.GlobalItems`（`Item.cs:17`）做一次交叉校验并写日志。
- 与 **汉化模组**：规则文件中的提示文案不经过 `Locale`，会永远是英文/原文；要么把提示统一走 `Locale.LoadLanguage` Postfix（`Patches.cs:28`），要么在文档中明确"规则名不翻译"。
- 与 **KrokMP（联机）**：规则表是**每客户端本地**的，联机时不同玩家的规则不同 → 同一份合成在主机与客户端可能落在不同容器里。物品所有权/同步由谁仲裁**未确认**；这是本方案最大的未知风险，联机场景建议强制忽略规则表（走内置默认）。
- 存档：**零存档影响**（规则只是决策输入）。但规则文件本身是**玩家资产**：它引用的 id 若来自已卸载的模组，会让相关规则整体失效。
- 风险：JSON 的语法错误必须降级到内置默认而不是抛异常（`SpawnResult` 在 Prefix 里抛异常会直接炸掉合成）。

**⑤ 工作量**：**大**（规则模型 + 解析 + 校验 + 排序内核 + 热重载 + 文档；约 400–600 行，且要写玩家能看懂的规则说明）。
**不可逆设计代价**：**规则语法（字段名与语义）一旦发布就是公共 API**。玩家会把 `liquid_rules.json` 提交到社区、贴进攻略；改字段名 = 破坏所有人的配置。同时"先匹配先赢"的语义一旦确定，就不能改成"最具体者优先"而不重写所有已有规则的心理模型。

**⑥ 玩家可感知**
- 优点：给硬核玩家最强的控制力（"所有 morphine 只进注射器，水只进水壶"），模组不用为每个新液体发版。
- 缺点：绝大多数玩家不会去编辑 JSON；出错时表现为"液体还是乱跑"，很难自我诊断。

## 方案 F：被动挽救（最小侵入 / 只做失败兜底）

**① 一句话目标**：**不接管**原版决策，只在原版"装不进去"的那一刻接管——保留原版行为作为默认路径，把兼容性风险压到最低。

**② 决策流程**

```
拆掉现有的整段 Prefix(Patches.cs:93-169 → return false 那套), 改为:

[Postfix RecipeResult.SpawnResult]     // 只在原版跑完之后观察
  if 本次合成结果是液体 且 原版已经在 body 上留下了一个 craftingbottle:
      // 原版走的是 RecipeResult.cs:59-64 的失败分支
      进入挽救链: 方案 A 分摊 → 方案 D 生命周期
  清除本批的 storing_in 通知缓存(原 Prefix 在 :130 做的那件事改到这里)

[Prefix RecipeResult.SpawnResult]      // 唯一保留的干预: 把"通知"包起来
  StorageLogic.storing_in = new List<string>();
  return true;                          // ← 永远放行原版
```

**③ 新增设置项**

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `liquids_rescue_only` | `SettingBool` | `true` | 只做兜底，不改变原版成功路径的选瓶 |
| `liquids_rescue_notify` | `SettingBool` | `true` | 挽救了才提示 |
| `liquids_verbose_diff` | `SettingBool` | `false` | 日志输出"原版选了谁 / 我们本来会选谁"，便于回归验证 |

**④ 兼容性与风险**
- **这是唯一一个真正解决"CUCoreLib 与 CraftingLogic 同时整体 Prefix `RecipeResult.SpawnResult`"冲突的方案**。现状是：CraftingLogic 的 `Patches.cs:168` 无条件 `return false`，导致 CUCoreLib 的 `SpawnCustomResult`（`RecipeRegistryPatches.cs:101-137`）**永远不执行**——虽然 CUCoreLib 的自定义物品仍能造出来（因为它同时补了 `Utils.Create`，`UtilsCreatePatches.cs:29-43`，而 CraftingLogic 走的是 `Utils.Create`，`Patches.cs:149-151`），但**两条自定义物品分支的差异（`CustomInstantiate.InstantiateReturn`、`component2.stack = new List<LiquidStack>()` 清空等）会静默丢失**。改成 `return true` 放行后，这个问题自动消失。
- 同样受益的还有 `Recipe.GetItemsForRecipe` / `Recipe.GetItemsForRecipeThorough` 的现有 Prefix（`Patches.cs:7-23`）：**未确认**其他模组是否也补（CraftingTweaks 只在 `AvailabilityBackend.Vanilla` 模式下直接调用 vanilla 实现，见 `_analysis\BetterInventoryLogic-改进与新增功能分析.md` 4 节）。
- 与 **CraftingTweaks**：它 Prefix `PlayerCamera.TryCraft`（priority 1000）并做批量合成——批量合成会让"一次合成一批液体"变成"N 次 SpawnResult"，方案 F 的兜底链必须是**幂等**的（每批只做一次归并/通知），否则一次性弹 N 条提示。
- 存档：零影响（不引入新持久化，不改写 `stack` 结构）。
- 代价：**能力上限被锁死**。你拿不到"原版为什么失败"的内部信息，也**无法实现"部分装填"**（因为原版失败时液体根本还没落地）——只能事后从临时瓶里搬，多了一次造瓶/拆瓶的中间态，且 `craftingbottle` 容量 1000（`Item.cs:6598-6615`）会让"其实装得下的液体"绕道临时瓶。

**⑤ 工作量**：**小**（删除多于新增：把 70 行替换实现换成 ~20 行观察钩子 + 兜底调用；约 -50 行净变更）。
**不可逆设计代价**：**上限锁定**。一旦发布"最小侵入"版本，后续想加"余量续瓶"就必须重新接管 `SpawnResult`——即把已经稳定运行的兼容性优势换回来，玩家会经历过一次行为突变。所以 F 更适合作为**实现载体**而不是终态（见推荐）。

**⑥ 玩家可感知**
- 优点：与原版和其他模组的行为差异最小；液体永远有地方去；不会再出现"某个模组的自定义物品被我这个 Prefix 吃掉"这类难排查的问题。
- 缺点：**没有任何"更好"的选瓶**——瓶子选得仍然和原版一样笨（只认单一液体且全装得下），只是失败后有人接手；玩家感受不到"更聪明"，只感受到"不那么糟"。

| 方案 | 玩家收益 | 实现成本 | 风险 | 对存档的影响 | 推荐指数 |

## 我的推荐与理由

**推荐：以 F 作为实现载体，v1 交付 A + D，B 作为低成本附加；C 放 v2；E 暂不做。**

1. **F 不是备选方案，而是所有方案的实现方式。** 现有 `Patches.cs:93-169`（`return false`）与 **CUCoreLib 的 `RecipeRegistryPatches.cs:101`** 整体争抢同一个方法，是本机环境里已经存在、且会随任何一个新模组安装而恶化的结构性冲突（`Patches.cs:98-105` 作者自己也承认）。把它换成"通知包一层 Prefix + 兜底 Postfix"，是**降低后续全部开发风险**的动作，应该先做、且单独做一次回归验证。
2. **D 优先级最高，因为它消灭的是"玩家会发帖骂人"的失败模式**：`Patches.cs:143` 先把临时瓶塞进背包、`:145` 再挂 `Object.Destroy(gameObject, 300f)`——液体在玩家包里静默蒸发。原版 `RecipeResult.cs:59-64` 同样如此，但正因如此，改它才是这个模组**最有辨识度的价值点**。默认建议"永不销毁"，并同时提供自动归并（把液体搬进长期容器后用 `DrainAll`/`Drain` 清空，让 `CustomItemBehaviour.cs:261-267` 的"空瓶自毁"接手清理）。
3. **A 紧随其后，成本极低而收益立竿见影**：`WaterContainerItem.cs:98` 的 `AddLiquid` 本来就返回实装量，现有 `LiquidStorageLogic.cs:92` 的 `SpaceLeft < amount → continue` 是纯粹的自我设限。改完后顺带把 `StorageLogic.storing_in` 从 `HashSet<string>` 改成有序列表，否则提示会少报落点。
4. **B 是本机的"性价比彩蛋"**：`favourited`（`Item.cs:24`）已经能由玩家在背包里一键切换（`PlayerCamera.cs:1878-1882`）、已经在名字里显示图标（`Item.cs:62`）、已经随存档保存（`SaveSystem.cs:56`）、还已经被原版用作文本提示（`PlayerCamera.cs:1477-1479`）。做一个"收藏的水壶=液体目标"只需很小的工作量，就能得到"玩家显式指定目标"的全部好处，**不需要任何新 UI**。唯一要处理的是它与"防误耗"的语义重叠（`RecipeItem.cs:29`），必须在设置项文案里说清楚。
5. **C 为什么放 v2**：它真正的价值取决于一个设计决策——**台账是"只影响选择"还是"影响数值"**。只影响选择（安全）时，它退化成一套更精细的排序规则，收益不如 A/D 直观；影响数值时，它立刻需要回答"原版 `Drink`/`Inject` 不读这个乘数"（`WaterContainerItem.cs:167 / :185 / :202`），变成一个说不太圆的承诺。先把 A/D/B 做扎实，再决定要不要碰纯度。
6. **E 为什么不做**：规则表把"决策"变成"公共 API"（字段名不能改），而它的直接受益者只有愿意编辑 JSON 的少数玩家；同时联机（本机装了 `KrokMP`）下"每客户端规则不同"的后果**未确认**，风险收益不划算。若确实想要"液体 X 优先存 Y"的轻量版，建议先做**固定 3 条内置规则 + 一个 `SettingDropdown` 档位**（例如"饮用水优先/危险液体隔离/全部随意"），把 JSON 留到有人真的要为止。
7. **无论选哪条，两件工程性动作必须做**：① 所有提示文案走 `Locale.LoadLanguage` Postfix（现有用法 `Patches.cs:28`）并且**不要提高 priority**，避免破坏与汉化模组之间"priority 200 用索引器覆盖"的隐式契约；② 读取 `Liquids.Registry`（`Liquids.cs:13`）一律用 `TryGetValue`，`CraftingLogic.cs:297 / :305` 的索引器写法是现存 P0 缺陷，会在遇到未注册液体时抛异常。
