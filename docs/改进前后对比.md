# 改进前后对比：BetterInventoryLogic → OptimisedCraftingSystem

> 口径说明
> - **旧模组**＝`BalaurBohemianBroken.BetterInventoryLogic`（`CraftingLogic.dll`，GUID `com.balaur.BetterLogic`，运行时版本串 1.0.4）。它的行为来自源码逐行阅读，行号一律写 `文件.cs:行号`，可直接打开 `cu-better-inventory-logic-1.0.5\` 核对。
> - **新模组**＝`OptimisedCraftingSystem`（GUID `maple.optimisedcraftingsystem`，版本 1.0.0），代码在 `OptimisedCraftingSystem\`。
> - 旧模组**没有**留下任何游戏内日志（它的 5 个补丁里没有一个写日志、没有 GUI、没有自检），所以旧模组那一列是**源码事实**；新模组那一列既有源码也有**实测日志**（见第三节）。
> - 两者**不能同时装**：新模组启动时检测到 `com.balaur.BetterLogic` 会在日志里报错提醒。

- 这一行说明整条链路真的跑通了：**开合成会话**（`Recipe.TryMake` 前缀）→ **自动选材**（挑中了耐久 0% 的垃圾袋）→ **算出这一槽实际会扣掉的量并写进日志** → **落点执行**（产物被装进了容器「垃圾袋」）。

## 四点五、与其它模组的真实交互（反编译实测，不是猜的）

「兼容并包含其它新模组添加的工具」这条要求，除了**物品与性质自动纳入**（本模组遍历的是游戏自己的物品池 `GetAllItemsThorough()` + 地面扫描，
任何模组新加的工具只要带 `Stats.qualities` 就自动参与性价比比较，无需为它写特例），还要看**补丁入口的先后**。
本模组在**会接管结果的入口**上一律用 `Priority.Low`(200)（HarmonyX 里数字越大越先执行，200 &lt; 别人常用的 400，等于主动让位）；
唯一一处例外是「恢复默认」的**通知型**前缀（`Priority.HigherThanNormal` = 500）——它返回 `void`、永不 `return false`、不改变任何结果，
只是置一个标记，所以必须最早跑，否则会被别人的 `return false` 一起短路掉（下表最后一行就是实测到的这种情况）。
实测结果如下：

| 入口 | 别人怎么挂的 | 与本模组的关系 |
|---|---|---|

结论：**合成与存放链路上没有任何一处是「两个模组都返回 false、互相覆盖」的硬冲突** —— 本模组在这些入口用 p200 让高优先级前缀先决定，
对方接管时本模组退让、对方不管时本模组接管。唯一需要「抢位」的是设置界面的「恢复默认」（QoL Unknown 会 `return false` 接管）：
那里本模组用的是**只置标记、不改变结果的"通知型"前缀**（提到 p500 先跑）并叠一层后缀兜底，既没有和对方互相覆盖，也没有破坏对方的逻辑。
这正是旧模组当年做不到的地方（它用 `Prefix return false` 整体替换 `RecipeResult.SpawnResult`，
把 CUCoreLib 的自定义产物直接顶掉）。

## 五、怎么自己复现这套对比

1. 备份并移走旧模组：`BepInEx\plugins\CraftingLogic.dll`（已备份到 `_backup\plugins-2025\CraftingLogic.dll`，SHA256 `24B276DE3E7A38CE23940996A6E06F3B78FA6F987DCD29EFDBE8B9056768F8EA`）。

3. 进游戏 → 日志里搜 `[自检]`，应看到 **14 行**：3 条关键（`Recipe.GetItemsForRecipe` / `GetItemsForRecipeThorough` / `TryMake`，缺了会打 Error）+ 11 条提示级（最后两条是兼容垫片 `RecipeItem.DoesUseItemType` 与新增的消耗前抢救 `RecipeItem.UseItem`，见四点五最后一行）；并确认语言是中文、字体是雅黑。
